# TotalRecall.Infrastructure — Agent Guide

The infrastructure layer owns all side-effects: storage, embedding, importers, ingestion,
telemetry, search, and Cortex sync. Pure logic lives in `TotalRecall.Core` (F#).

**AOT requirement**: `IsAotCompatible=true` and `InvariantGlobalization=true` are set in the csproj.
No reflection, no dynamic code generation. All JSON via source-generated `JsonContext`.

## Storage Layer

### IStore

```csharp
interface IStore
{
    Task<Entry?> GetAsync(string id, ...);
    Task<IReadOnlyList<Entry>> ListAsync(Tier tier, ContentType type, ...);
    Task StoreAsync(Entry entry, ...);
    Task UpdateAsync(string id, ...);
    Task DeleteAsync(string id, ...);
    Task MoveAsync(string id, Tier targetTier, ...);  // for promote/demote
}
```

**All-or-nothing transaction (git sync groundwork).** `SqliteStore.BeginTransaction()` returns a
`SqliteStoreTransaction` (not on `IStore`) offering insert with its vector, move between tiers, delete,
update, `SetSticky` (hot only), `RekeyMemory` (git sync part 5, below) and an `import_log` write as one unit: `Commit()` makes them all take effect,
`Dispose()` without `Commit()` rolls everything back. Embeddings are computed by the caller before it opens.
It runs on the store's single connection, so while one is open no other code may use that connection
(Microsoft.Data.Sqlite fails a stray command with `InvalidOperationException`), and a second
`BeginTransaction()` on the same store throws. The statements live in `Storage/SqlRows.cs` (`SqlRows`,
`VecRows`), shared with `SqliteStore`'s own methods. An internal `BeforeStep` seam lets tests inject a
failure at a named step. The git sync applier, pusher, review service and setup service use it, all through
`SqliteStore.BeginImmediateTransaction`.

**Git sync cycle (`GitSync/GitSyncCycle*.cs`; rules in `Core/SyncCycle.fs`).** `GitSyncCycle(GitClient, RepoGuard, SqliteStore, IEmbedder, GitSyncPaths, CycleSettings(Address, Branch, MachineLabel, HotMaxContentChars, LockWait, DeleteGuardPercent = 20), Func<DateTimeOffset> clock, Func<long> nowMs).RunAsync(ct)` returns a `CycleOutcome`: `Done(CycleSummary)`, `NotJoined`, `Refused(reason, step)`, `Busy`, `Failed(step, kind, message, published)` or `Cancelled`; it never throws for the state of the store, the repository, the file system or the network, and prints nothing (the one stderr line is the `ExceptionLogger.LogChain` of an unexpected exception). The constructor throws when `Address` is empty, is not the guard's `ConfiguredRemote`, or the paths' clone directory is not the client's. One instance should live as long as the process (the damaged-clone state is per instance). Order, all under the sync lock: **identity** (`GitSyncFetcher.CheckIdentityAsync`: `NotJoined` records nothing, `Refused` is recorded; it runs before the scan so a copied data directory never issues stamps), **locks** (`RemoveStaleLocks`, best effort), then an *attempt*: **scan**, **clone** (a missing clone is cloned; a directory that is not a sound clone is moved aside with `CloneSideline.Move(.., "broken", ..)`, never deleted, and cloned again), **fetch** (a failed fetch of kind `NotARepository`, or `Other` / `RemoteNotFound` followed by a failing local probe, is damage: replace the clone and restart from the scan), **apply**, the **gate** (`SyncCycle.pushDecision`: an incomplete pull ends `Done` with `PushSkipped = "pull-incomplete"` and no push) and the **push** (a non-fast-forward restarts from the scan, at most three pushes per cycle; a push `Failed("Clone")` followed by a failing probe is damage too). **Once per process** the cycle moves one damaged clone aside; the second damaged clone gives `Failed(clone, CloneUnusable)` and is kept, so every later `RunAsync` on the instance returns it at once, without the lock, a read or a write. A clone that failed or was cancelled leaves a partial directory that is deleted (or moved aside as `partial`) and never counts. **Recording** (the last act under the lock; `OnStep("record")` fires only when something is written): `Done` deletes `git_sync_last_error` and then sets `git_sync_last_ok` (also for an incomplete pull: nothing failed); `Failed` and `Refused` set `git_sync_last_error` to `SyncCycle.errorLine(...)`; `Busy`, `NotJoined` and `Cancelled` write nothing; a failed write is swallowed. A cancel is decided from the token after each part returns, except that once the push command has succeeded the cycle is `Done`. Test seams: `OnStep(step)` (`lock`, `identity`, `locks`, `scan`, `clone`, `fetch`, `apply`, `push`, `record`), `BeforeMetaWrite(key, value)`, `DeleteDirectory`, `MoveDirectory`. Known limit: a partial clone directory that can be neither deleted nor moved aside stays, can hold a `.git` that passes the sound-clone check, and then counts as damage on the next cycle. Nothing calls the cycle until a later part of 1b-iii adds `sync now`; a source scan test (`GitSyncCycleCallerTests`) pins that nothing outside `GitSyncCycle*.cs` names it and nothing outside the pusher and the cycle names the pusher. The cycle reads no configuration and has no command; the caller (1b-iii `sync now`, milestone 2 timer and session hooks) builds the settings (`DeleteGuardPercent` is passed to the applier's `ApplyOptions`; the caller takes it from `[git_sync] delete_guard_percent`). Held items, applied deletions and repush markers never make a pull incomplete (milestone 1b-ii), so the push runs with them in play. Tests: `CycleRig` (one machine) and `TwoMachineRig` (two machines, each with its own database, clone and clocks, on one bare remote) in `tests/TotalRecall.Infrastructure.Tests/GitSync/`; the deletion scenarios across two machines are `TwoMachineTests` and `GitSyncCycleDeletionTests`.

**Git sync push (`GitSync/GitSyncPusher*.cs`; rules in `Core/SyncPush.fs`).** `GitSyncPusher(GitClient, SqliteStore, branch, machineLabel).PushAsync(apply, scan, ct)` returns `PushOutcome`: `Pushed`, `NothingToPush`, `NotReady`, `NonFastForward` or `Failed(kind, message, published)` (`published` is `No`, `Yes` only after the push command succeeded, or `Unknown`). The caller holds the sync lock and passes the summaries of the scan and a **complete** pull; only the cycle calls it (and its tests), and nothing calls the cycle until a later part of 1b-iii adds `sync now`. Order: **prepare** (readiness: `apply.Complete` and `_meta` last sha equal to `apply.Head`; write `.git/info/attributes` with every filter off, then `reset --hard L` and `clean -fd`, `HEAD` must be `L`; read the tree at `L` as git objects with `PullTree`; select candidates and decide the exclusions), **plan** (one `BEGIN IMMEDIATE` transaction before any file is written: re-read each row and entry, defer an entry that no longer agrees with its row (`changed-since-scan`), build the record (a new record, or a patch of the record at `L` through `RecordPatcher`), check the limits (`SyncValidation.checkWritable`), write the block marks and the `pushing_stamps` of the entries that will be written; a failure rolls it back whole), **write** (temporary file under `.git`, renamed over the record path; `StagePaths` in batches of 100; the staged set must be exactly the written paths (added or modified) and the removed paths (deleted); one commit `sync: <label> +<new> ~<changed> -<removed>`; `push` without force; any failure up to the push command resets and cleans the clone; a non-fast-forward leaves it as it is and the next prepare resets it), **finalize** (one transaction: `base_json`, the cleared pending stamps, `pushing_stamps`, the writer's block marks, then `_meta.git_sync_last_sha`; then the protective ref; the token is never consulted after the push command succeeded). The comparison columns are left alone so an edit after the scan is still seen. Test seams: `BeforePlanTransaction`, `BeforeStep(id, step)` (`reread`, `plan`, `pushing`, `block`, `write`, `stage`, `commit`, `finalize`, `meta`, `ref`), `BeforePush`, `TransactionCount`. The cycle (1b-i-4) removes a stale `.git/*.lock` under the lock before it runs and does not push after a `Refused`, `Failed` or incomplete pull; only a deferral or a cancellation makes a pull incomplete (no decision postpones since conflict review, #164). **Deletions and repair (milestone 1b-ii).** *Removals* (D14): each id of `apply.PushDeletions` that is still one of the scan's `LocalDeletions` and whose record at `L` is accepted, unobstructed and not named by a rejected path (`SyncPush.removable`) has its record file deleted and staged as a removal in the same commit; any other is listed in `Skipped` as `removal-not-possible` and left alone. A push with removals only is a push, the staged-set check expects each removed path once as a deletion, and `PushSummary.Removed` lists them. *Write-back* (D15): a candidate with a base, no accepted record at `L` and a pending content stamp (a text edit beat a remote deletion) is written as a new file from its `base_json` patched with the entry's groups and the fresh stamp (counted as `+`; unknown fields of the base survive). *Repush* (D16): a row with a `repush_groups` marker is a candidate even with nothing pending; each flagged group with no pending stamp is set, in the record at `L`, to the base's value and stamp (`SyncPush.repushPlan`, no clock call; nothing local-only such as a declined pin or a local demotion enters the record), the base's stamp goes into `pushing_stamps`, and the finalize clears the marker (a failed or non-fast-forward push keeps it; a repush whose record already says what the base says writes nothing and clears it). A base whose `source` this version cannot parse keeps the repository record's source in a repush. *Held entries* (D17): a candidate with an open `held-delete` item (read with `GitSyncReviews` when the push prepares) is excluded as `held-delete` and writes nothing, so a tag, pin or promotion cannot write a vanished record back. `record-missing` now covers only a row with a base, no record and no pending content stamp (defensive after a complete pull); `not-reconciled` is unchanged. *Finalize* (D14): after a pushed commit each removed id's `active` row becomes `forgotten` in the same transaction (base kept; pending stamps, `pushing_stamps` and `repush_groups` cleared), even when a memory with that id exists again (the next scan reactivates it and the next push republishes it). A kill after the push command and before the finalize is repaired by the next apply (record absent, entry gone, base present: the row becomes `forgotten`), with no second commit. Test seams gain the `forget` step. **Secret re-check (milestone 1b-iii part 1, #161, spec D5).** The scan runs before the apply, and the apply can write text or tags the scan never saw (a merged tag union; a restore, `swap` or `merge` later), so the push checks again. The **preparation** (outside any transaction) runs `SecretDetector` (default `SensitiveContentScanner.ScanSecrets`) over the text, project, scope and each tag of every candidate that is not excluded, guided by `SyncSecret.precheck`, and keeps a `SecretCheck(Key, Hit)` per candidate; a candidate whose row already carries `secret-detected` is excluded and listed in `Skipped` with the reason `secret-detected` (other non-writer reasons keep `blocked-elsewhere`). `PlanOne` only compares keys inside the plan transaction (the detectors never run while `BEGIN IMMEDIATE` is held): a key that differs from the prepared one defers the entry as `changed-since-scan`, a candidate with no prepared key is deferred (`unreadable-entry` when the re-read is absent, else `changed-since-scan`), and a hit that is not allowed writes the row with `blocked_reason = 'secret-detected'` and `blocked_hash` = the key in the same transaction, lists the id in `Blocked` with that reason and builds no record, patch or write-back for it. **The pusher applies only the Block outcome**: it never clears a secret mark or reads `allowed_hash` except to let an allowed entry through, and `secret-detected` is not a writer reason, so `SyncPush.markAction` and the finalize's own-mark test leave it. No record holding a token or key is produced by the pusher, whatever produced the text.

**Git sync pull (`GitSync/GitSyncFetcher.cs`, `PullTree.cs`, `GitSyncApplier*.cs`, `GitSyncAliases.cs`, `PinPlanning.cs`, `LocalEntryReader.cs`, `BaseRenderer.cs`, `GitSyncIssues.cs`, `GitSyncReviews.cs`; rules in `Core/SyncApply.fs`, `Core/SyncMerge.fs`, `Core/SyncDeletion.fs`, `Core/SyncPin.fs` and `Core/SyncAlias.fs`).** Two classes, called in order by the cycle (milestone 1b-i-4; nothing else calls them, and nothing calls the cycle until a later part of 1b-iii adds `sync now`).
- **`GitSyncFetcher.FetchAsync`** (cycle step 2) returns `FetchOutcome`: `Fetched` / `NothingNew` (a `FetchResult(Head, Last, Proven, NothingNew)`), `Refused(reason)` or `Failed(kind, message)`. It never writes the store. Order: read `L` (`git_sync_last_sha`, only when 40 or 64 lowercase hex), the identity half of the guard (join state and host identity, no clone and no network), `ls-remote`, then either `NothingNew` (the head equals `L` **and** the clone holds `L`: no fetch and no reset, the full guard runs at `L`) or `fetch`, `R` from `rev-parse` of the tracking ref, the full guard at `R`, the proof state, and only then `reset --hard R`. **Proven** means there is an `L`, `L` is an ancestor of `R` (or equal) and `refs/total-recall/last-synced` equals `L`; a ref that is a strict ancestor of `L` is repaired in place (`UpdateLastSyncedAsync`); a `Tri.No`, `Tri.Unknown`, missing or elsewhere ref is just unproven; a git call that gives no answer is `Failed`. A manifest that could not be read because a git call failed or was cancelled is `Failed`, never `Refused`.
- **`PullTree.ReadAsync`** reads the tree at `R` as git objects (`ls-tree`, `diff-tree`), never the working tree: the listing alone decides what is present and what is rejected (`SyncTree.classifyRecordEntry`; a rejection names an id only for the exact path `memories/<shard>/<id>.json`); the diff, only when proven, gives the ids whose record changed.
- **`GitSyncApplier.ApplyAsync(fetch, scan, ct)`** returns `ApplyOutcome`: `Done(ApplySummary)` or `Failed(reason)` (the listing, the rows or the `L` writes failed). It builds the visit set (`SyncApply.visitSet`, united with the scan's skipped ids, every id with a `held-delete` item, open or approved, every id with a pin item in any of its four states and every id with a `conflict` item), decides each id in ordinal order with `SyncMerge.decide`, and applies each in **one `BEGIN IMMEDIATE` transaction** (`ApplyOne`): re-read of the row and the entry (any difference from the decision's inputs, including an edit the scan has not stamped, is a **deferral**), the store operations, the `git_sync_entry` row (comparison columns from the stored entry, so a scan right after stamps nothing), the `import_log` row for an insert (`git-sync`, `sync:<id>`) and the removal of the entry's `apply-failed` row. A busy database defers and **stops** the apply (the rest is counted `NotAttempted`). **Nothing postpones** (conflict review, #164, removed `SyncApply.postponement`; `ApplySummary.Postponed` and `PostponedEntry` stay for their shape and are always empty): a decision with a `NewPin` or `PinEdit` request is carried out and writes its pin item (see "Git sync pin review" below), and a text conflict (FC4, FC5, NC4) is carried out like any decision and files its loser as a `conflict` item in the same transaction, also when it carries a `NewPin` as well (see "Git sync conflict review" below). **Aliases (part 5, #165).** A W1 insert whose record's origin hash names a different local memory is skipped and recorded in `git_sync_alias` (the `alias` step), and before the deletion preview the **alias pre-pass** (`PrepareAliases`) picks the converging and ignored ids: a converging id converges onto its canonical record in its own transaction (`ApplyConvergence`) instead of `ApplyOne`, an ignored id is decided as the plain `Ignore`, and neither is counted by the preview or held by the unproven fallback (see "Git sync alias detection and convergence" below). **Deletions (milestone 1b-ii).** Before the first entry transaction a **preview** decides every deletion candidate (a visited id with no accepted record and no rejected path, or a local deletion whose accepted record parses; never a scan-skipped id) with the same input as the real decision, open held item included, writes nothing, and counts `DeleteEntry` as remote and `PushDeletion` as local; the limit is `SyncDeletion.guardLimit(ApplyOptions.DeleteGuardPercent, active rows at the start of the pull)` (`ApplyOptions(HotMaxContentChars, DeleteGuardPercent = 20)`), and a direction over it has each of its deletions turned into a hold with the cause `guard` (`ApplySummary.GuardTripped` gives the count and limit). The carry-outs, each inside the entry's transaction: a `DeleteEntry` deletes the content and vector rows and makes the row `forgotten` (base kept; pending stamps, `pushing_stamps` and `repush_groups` cleared); a `HoldDeletion` upserts one open `held-delete` item through `GitSyncReviews` (direction `remote` or `local`, cause `guard`, `unproven` or `sticky`, the record's blob id in R (NULL for a `remote` hold), `arrived_at` the applier clock; a local hold also clears the pending stamps; the entry stays); a `CloseHeldDelete` deletes the item first, so a decision that closes and holds leaves exactly one open item; an open local item the decision leaves open has its `record_hash` refreshed to the record's blob id when that differs (`refresh` step, after `close`/`hold`; counted `Updated`, nothing new in the summary); a `PushDeletion` writes nothing to the store and lists the id in `PushDeletions` for the push; a `LeaveEntry` with `FreshContentStamp` (a text edit beat a remote deletion) issues a new pending content stamp at the `row` step; a `MergeGroups` replaces the row's `repush_groups` with its repush flags (`SyncApply.repushMarker`). The open items are read once per pull (`GitSyncReviews.ReadOpenHeld`) and passed to `decide` as `HeldDelete`. **Approved items (milestone 1b-iii, D4)** are read beside them (`ReadApprovedHeld`) and decided by the one helper the preview and the loop share (`Decide`, with `SyncDeletion.approvedUse` and `closeApproved`): only in W8's shape (row `active` with a base, entry gone, record present) and with the record's blob id equal to the item's hash is the id decided as proven with no held item, so it is a `PushDeletion` even in an unproven pull, not counted by the preview and never converted by the guard, and the item stays `approved`; a different blob id re-opens the item with that hash (`reopen` step) and decides W8.2; any other shape decides with the real proof and no held item; the item is removed when the entry is present again, the record is absent or the decision inserts. A scan-skipped id removes its approved item in a small transaction (`close` step) and is listed in `ClosedHeld`, as does an id whose record in `R` is rejected or invalid while its entry is present again (not a local deletion); when that transaction fails the id is deferred. The transaction re-reads compare the open or approved item (`ReadHeldItem`) against the item as the pull read it, and the push's `Forget` removes the id's item before its early return. A local deletion whose record in `R` is rejected or accepted by path but invalid is **skipped** (`Skipped`: `the record is rejected` / `the record is invalid`): never decided, counted or written, and it does not hold `L`. **Unproven fallback hold:** in an unproven pull a deletion candidate of a row that was `active` with a base (a vanished record whose entry exists, or a local deletion with an accepted record) whose entry ended failed, skipped or scan-skipped, so that its own transaction wrote no hold, gets an open `unproven` item in a small transaction of its own after that (`hold-unproven` step; an open item of the same direction, or an approved item against a local hold, is kept; an open item of the other direction, or an approved item against a remote hold, is replaced); if that write fails the entry is deferred and `L` stays, so a later proven pull can never delete it. `ApplySummary` adds `Deleted`, `Held` (id, direction, cause), `GuardTripped`, `PushDeletions`, `ClosedHeld`, `Notes` (`edit-beats-deletion`, `pending-changes-dropped`) and `RepushMarked` (id, groups). `GitSyncReviews` is the plain SQL of `git_sync_review`, every member with the caller's transaction and every statement restricted to its own kind: the held members (`ReadOpenHeld`, `ReadOpenHeldItem`, `ReadHeldItem`, `ReadApprovedHeld`, `UpsertHeld`, `ApproveHeld`, `ReopenHeld`, `RefreshHeldHash`, `DeleteHeld`; `HeldItem.State` is `open` or `approved`) read and change only `held-delete` rows (`payload_json` is `{"cause":"<cause>"}`); the pin members (`ReadPinItems`, `ReadPinItem(id, kind)`, `UpsertPinItem`, `MarkPinUnseen`, `ResolvePinItem(id, kind, state)`, `DeletePinItem`; `PinItem.State` is `open`, `unseen`, `approved` or `declined`, and a pin member that writes throws when given any other kind) read and change only `new-pin` and `pin-edit` rows (no direction; `payload_json` `{}` for an item a pull made, `{"origin":"restore"}` for one a restore opened, read back as `PinItem.Origin`); the conflict members (`ReadConflictItems`, `ReadConflictItem`, `UpsertConflictItem(item, keepArrivedAt)`, `MarkConflictUnseen`, `DeleteConflictItem`, `RekeyConflictItem(from, to)`, and `ConflictPayload`/`ReadConflictLosers` for the payload; `ConflictItem.State` is `open` or `unseen`) read and change only `conflict` rows. The one cross-kind read is `HasAnyItem(id)` (a review row of any kind and state; alias convergence's "the canonical id is free" check, and `RekeyConflictItem`'s guard: it refuses with `InvalidOperationException`, writing nothing, when the target id has any review row). `L` (`git_sync_last_sha`, then `refs/total-recall/last-synced`) advances only for a complete pull (every id processed, nothing deferred). `apply-failed` rows record a failed entry (attempts, blob id, a one-line detail) and also `scan-skipped:` / `unreadable:` entries that were not applied (no attempt counted; never overwrite a real failure); `rejected-record` rows are keyed by `sanitizeText(path)` and swept at the end of a pull that processed every id. A rejected path is never read as a deletion (and a local deletion with one is skipped, above). `GitSyncIssues` (`apply-failed` and `rejected-record` rows: `ReadOpen`, `Read`, `Upsert`, `Delete`) and `SyncSql` (`GetMeta`/`SetMeta` on a given transaction: `SqliteStore.GetMeta` has none and throws while one is open) are the plain SQL the apply uses. Test seams: `BeforeEntry`, `BeforeTransaction`, `BeforeEntryStep(id, step)` (the store transaction's own steps, `rekey-row` and `rekey-parent` among them, plus `reread`, `row`, `close`, `hold`, `refresh`, `reopen`, `pins`, `alias`, `rekey`, `converge`, `hold-unproven`, `issue`, `commit`, `write-issue`; the steps of a convergence are reported under the other id), `TransactionCount`. **Store groundwork the apply uses:** `SqliteStore.BeginImmediateTransaction`, `SqliteStoreTransaction.ReplaceEmbedding`, `SqliteStoreTransaction.RekeyMemory` (part 5), and `UpdateEntryOpts.SourceTool` / `ClearSourceTool` / `CreatedAt` (Postgres refuses them). A null vector array must stay "no vector" (`Memory(...)`): the implicit array-to-memory conversion would make it an empty one.

**Git sync conflict review (`GitSync/ConflictItems.cs`, the conflict members of `GitSyncReviews.cs`, the item step of `GitSyncApplier.Entry.cs` and `PinPlanning.cs`, `ReviewService.Conflicts.cs`, `ReviewService.List.cs`, `Cli/Commands/Sync/ReviewCommand.cs`; rules in `Core/SyncConflict.fs`, refusals in `Core/SyncSetup.fs`; milestone 1b-iii part 4, #164).** When both machines changed the text of one memory since their common base, the pull applies the clock's winner at once and keeps the losing text as an alternative; nothing waits. **The item.** One `git_sync_review` row of kind `conflict` per id, keyed `(entry_id, 'conflict')` (no schema change), independent of a `held-delete`, `new-pin` or `pin-edit` item of the same id. `direction` NULL; `state` `open` or `unseen` (every reader treats `unseen` as open); `machine` the machine id of the newest loser (8 hex digits); `arrived_at` the applier clock of the first conflict, kept when a later one is appended; `payload_json` `{"losers":[{"side":"local|remote","text":"...","stamp":"<stamp text or empty>","machine":"<8 hex>"}, ...]}`, oldest first, written with `Utf8JsonWriter` (`GitSyncReviews.ConflictPayload`, read back by `ReadConflictLosers`). `side` `local` is the text this machine wrote, `remote` the record's; a loser with no stamp (NC4 with no row) takes this machine's id (`_meta git_sync_machine`, read once per pull outside the transaction). The applied text is not stored: it is the stored entry's text, read live. `SyncConflict.append` is the one append rule: a loser whose text equals a kept one is not added again, and a ninth drops the oldest (`maxLosers` = 8). Losers stay local: a payload is never a record, so a losing text that holds a token is never pushed. **The shown hash** (`SyncConflict.shownHash applied losers`: SHA-256 over `total-recall/review/conflict/v1\n`, the applied text as a field (presence byte, 4-byte big-endian length, UTF-8 bytes; `None` is the byte 0), a 4-byte big-endian count and each loser's text as a field in payload order; stamps and machines are not hashed) is the item's `record_hash`, of the stored entry's text and the losers after the carried-out decision. **Arrival (D3).** The decision is carried out as any other (`SyncMerge.decide` is unchanged): FC4 keeps the local text and its pending stamp (the push writes it) and files the record's text; FC5 and NC4 take the record's text, clear the pending content stamp and file the local text. The loser filed is the decision's `Conflict` payload, fixed by `decide` (the applier never re-reads the local text for it). It is planned in the item step with the pin rules (`PinPlanning.Plan`, `PinPlanning.HasWork` is the one gate: a pin item, a conflict item, or a pin or `Conflict` request): the pin reconcile and arrivals first, then the conflict reconcile (D4) and then `ConflictItems.Arrive` for each `Conflict` request, over the entry as the pin rules leave it (with pin-edit rule 4, the text of the post-decision base), so the plan before `BEGIN IMMEDIATE` and the one recomputed inside it read the same text. No item: write it `open` with that one loser, its machine and the hash; an `open` or `unseen` item: append, and when the hash changed write `unseen`, the new hash and the newest loser's machine; an unchanged hash writes nothing. `ConflictItems.Diff` turns the result into one `ConflictWrite` (`Remove`, `Upsert` with the payload, hash and machine, `Fresh` for a new row, also when the reconcile removed the stored item and an arrival of the same pull filed a new one, so it gets a new `arrived_at`, or `MarkUnseen`), `PinPlan.Matches` compares it by value (payload and hash included), so a recompute that differs **defers** the entry, and the re-read at the start of the transaction compares the conflict item read before it by value. After the carried-out decision the base equals the record, so a repeated pull decides the content group `Unchanged`, plans nothing and opens no transaction. `ApplyDrop` deletes the id's conflict item in its own transaction. A conflict item whose id is not decided in a pull (moved to knowledge, skipped, failed) is left for the next pull that decides it. **Reconcile (D4)**, `SyncConflict.reconcile` through `ConflictItems.Reconcile`, first match: (1) row `forgotten` or `left`, or the entry absent and **no deletion held after this decision**: remove; the entry absent with a deletion held: keep the item unchanged; (2) losers whose text equals the entry's text are dropped, and with none left the item is removed; (3) the shown hash differs from the item's: `unseen` with the new hash, the kept losers and the newest kept loser's machine; (4) keep. "Held after this decision" is one input, `SyncConflict.heldAfter decision heldOpenOrApproved`, computed once per entry from the decision (after the guard's conversion, `SyncDeletion.holdInstead`) and the held item the pull read, and never read from the database (the item step runs before the hold is upserted): `HoldDeletion` is held, `PushDeletion` and `DeleteEntry` are not (so the pull that carries out a W8.3 deletion or an approved hold removes the item in that pull), anything else is held when the id's item is open or approved and the decision does not close it. So a held deletion (W8.4 unproven, a guard hold, W8.2 over an open hold) keeps the item, which holds the only copy of a record-wins conflict's local text, and a later `restore` lists it again; an accepted remote hold or a pushed local deletion forgets the row, and the next pull (conflict ids are always visited) removes the item. A missing row is not a reason to remove: the items survive `sync init` and `sync join`. A local edit after the conflict does not close the item (rule 3 marks it `unseen`); a text that came back equal to a loser drops that loser (rule 2). The push never excludes an entry for a conflict item (`SyncPush.exclusion` reads `held-delete` only), so an unanswered conflict blocks nothing: the cycle completes and the item is only listed. **The answers (D6)**, `ReviewService.KeepAsync(id, shownHash)`, `SwapAsync(id, shownHash, loserIndex)` and `MergeAsync(id, shownHash, text)`, in the held-deletion frame (`RunAsync`: the sync lock, migrations, one `BEGIN IMMEDIATE`) with `CheckConflict`, in this order: a conflict item `open` or `unseen` (`no-conflict-item`); a shown hash (`shown-hash-required`); the entry read for all three verbs (absent: `stale-item`, nothing written, "the next sync closes the item", or, with an open or approved `held-delete` item, "restore or accept the held deletion first"; in two tiers or unreadable: `unreadable-entry`); for `swap` and `merge` the row `active` with a base (missing: `failed`, "not synced yet; run a sync first", the state after `sync join` until the first cycle; otherwise `failed`), while `keep` reads no row; the shown hash equal to the live one (`SyncConflict.shownHash` of the entry's text and the payload's losers; a difference is `stale-item` and the item's update to the live hash and `unseen` is **committed**, `CheckOutcome.CommitRefusal`, the one refusal that writes); the chosen text: `swap` takes loser `loserIndex`, 1-based in the list as shown (newest first; may be omitted with exactly one loser; else `unknown-loser`), and a `remote` loser must survive the list's sanitiser unchanged (`unshowable-text`; a `local` loser is swapped as it is), `merge` refuses an empty or whitespace-only text, a NUL or more than 262144 UTF-8 bytes (`bad-merge-text`); for a sticky entry the chosen text within `tiers.pinned.max_content_chars` (0 or less: 500; `over-pin-cap`). A chosen text equal to the entry's only removes the item. *Keep* removes the item and changes nothing else (a pending push stays pending). *Swap* and *merge* set the text, and only the text (`ApplyPlanning.ApplyText`: project, scope, type, source, `created_at`, tags and tier untouched, except that a hot, non-pinned entry over `tiers.hot.max_content_chars` is stored warm as `TakeTheirs` does), with the vector computed before the transaction (`EmbedConflictText`; null, with no embedder created, whenever a check would refuse; inside the transaction a vector of another text is `stale-item`); the row gets a content stamp issued above the greater of the base's content stamp and the row's pending one (`IssueStamp`; none to issue: `failed`, nothing committed), left **pending**, and its comparison columns from the stored entry (`WithComparison`, so the scan stamps nothing more); the item is removed and the answer carries `ReviewService.RevertWarning`. Nothing is pushed by an answer: the next cycle pushes the text as an ordinary edit, which wins on every machine where the memory is not pinned (where it is pinned it is held there as a `pin-edit`); a text holding a token is blocked by the scan's secret pass and the push's own re-check. Fault seam `BeforeStep`: the store steps, `row`, `resolve` (the last write). **List and CLI (D7).** `List()` returns open and unseen conflict items (by id, then kind) with the shown hash computed live (with no applied text while the entry is absent), `Machine` the item's (an empty stored machine or stamp is shown as none), `Text` the applied text (source `local entry`; no text while the entry is absent, with the source `held deletion` when an open or approved `held-delete` item exists) and `Losers` (`ConflictLoser`: side, machine, stamp, text, `TextCut`; newest first; empty for the other kinds), under the list's text rules. The hidden `sync review keep <id> --shown <hash>`, `swap <id> --shown <hash> [--loser <n>]` and `merge <id> --shown <hash> --text-file <path|->` (`ReviewCommand`) require `--shown` (8 or more hex digits, a prefix of the item's hash; usage error, exit 2, without it); `--loser` is an option of `swap` only and `--text-file` of `merge` only; the text is read as strict UTF-8 (a leading BOM dropped), at most 262144 bytes, and passed exactly as read (no newline is trimmed); an unreadable, invalid or oversized input is a usage error that changes nothing, while an empty file reaches the service (`bad-merge-text`, exit 1). `list` prints a conflict as a header `<id>  conflict  <state>  arrived <ISO>  shown <h|->`, the applied text block (or the line `entry deleted here, deletion held`) and one `loser <n>  <side>  machine <m|->  stamp <s|->` header and text block per loser, numbered from 1 (the newest). `accept`, `restore`, `approve`, `decline` and the bulk forms ignore conflicts, and the conflict verbs answer conflict items only (`no-conflict-item` for an id without one). **Helper for the alias pass (milestone 5).** Part 5's convergence does not use it: it re-keys the other id's conflict item to the canonical id and files the arrival through the ordinary plan (see "Git sync alias detection and convergence" below). `ConflictItems.Append(tx, id, loser, nowMs)` files a loser without a merge decision inside the caller's store transaction: it reads the item and the stored entry, applies the same arrival rule (`Arrive`, `Diff`, `Write`) and writes what changed; an entry that is absent, in more than one tier or unreadable throws `InvalidOperationException` before anything is written, which the alias pass must handle. Tests: `SyncConflictTests.fs`, `GitSyncReviewsTests`, `ConflictItemsTests`, `GitSyncApplierConflictTests`, `ReviewServiceConflictTests`, `SyncCommandTests` and `ConflictReviewCycleTests` (whole cycles over `TwoMachineRig`: two text edits leave the later one on both machines and the loser listed on B, whichever side wins; `keep`, `swap` and `merge` each leave the stated text on both machines; a second conflict keeps both losing texts; an unanswered conflict blocks nothing; a swapped text holding a token is blocked by the scan and skipped by the push, and with a scan that misses it the push's own check holds it back).

**Git sync alias detection and convergence (`GitSync/GitSyncAliases.cs`, `GitSyncApplier.Alias.cs`, `GitSyncApplier.Converge.cs`, the `alias` step of `GitSyncApplier.Entry.cs`, `SqliteStoreTransaction.RekeyMemory`; rules in `Core/SyncAlias.fs`; milestone 1b-iii part 5, #165).** A memory imported from a host file before git sync existed has a random id on each machine, so once synced the same file is two records with the same `origin.hash`. The pull never shows the person that duplicate and never reads the later disappearance of the other record as a deletion. No schema change: `git_sync_alias` (migration 18) is used as it is. **The lookup (D1).** `GitSyncAliases.ImportTargets(record id, h)`: the `target_entry_id` of every `import_log` row with `content_hash = h` and `target_type = 'memory'`, from **any** `source_tool` (a host import, or the `git-sync` row an earlier pull of a record with the same origin wrote), that exists as a memory in the hot, warm or cold table, is an eligible id (`SyncValidation.isEligibleId`) and is not the record's id. `PlanSkip` gives `null` with no target, else an `AliasPlan` from `SyncAlias.detect`: the group is the record's id, the targets and both ids of every `open` row with the same origin hash; the canonical id is the ordinal minimum; one `open` row `(canonical, x, h)` is planned for each member that is the record's id, a target or a local member of an open row, is not the canonical id and has no row yet in any state (`InsertOpen` is `INSERT OR IGNORE`, so a `resolved` group is never reopened and rows are never rewritten). **The skip.** In `ApplyCore`, right after `Decide`, a W1 decision (no row, no local entry, `InsertFromRecord`, a record with an origin) runs `PlanSkip`; a plan replaces the decision by `SyncAlias.skipInstead` (the plain `Ignore`: no row, no `new-pin` item, no notes), whichever member is canonical. The skip is decided per visit, from the `import_log` rows, the alias rows' ids and the entries but not the rows' state, so it is the same on every pull and in an unproven pull; a fresh machine whose first pull holds both records of a group inserts the first visited and skips the other. The plan is recomputed inside the transaction (`alias` step) and a difference (an importer wrote a matching row or deleted the target in between) defers the entry; a busy lookup defers, another SQLite error fails the entry. A repeated pull plans an empty `AliasPlan` and opens no transaction. A skip is a `NoOp`, writes no `git_sync_entry` row and never defers by itself, so it does not hold `L`. **The pre-pass (D2).** `PrepareAliases` runs after the rows, held items and `blobs` map are read and before the deletion preview, and only when some `active` row with a base has no path in `R`. Q is those ids that are eligible, have no held-delete item (open or approved: condition 7) and a readable local memory; their candidates are the canonical ids of their `open` rows (a NULL origin hash never counts) and of this pull's detections (each W1 candidate whose origin hash is one of the `import_log` hashes of Q's ids runs `PlanSkip`, so a canonical record added in the same pull counts like an open row). A W1 candidate's blob is read first, and only one whose origin hash is a hash of an id of Q (its `import_log` hashes or the hashes of its open rows) gets the local read and knowledge check, so a record that can alias nothing here never fails the pre-pass. The target of an id is the lowest candidate whose record is accepted at `R` and parses (`SyncAlias.target`), read through the shared `blobs` map so no blob is read twice; the target is **free** when no memory, knowledge entry, `git_sync_entry` row or review row of any kind (`GitSyncReviews.HasAnyItem`) has its id. `SyncAlias.choose` makes the lowest qualifying member per target a **converging** id and every other id with a candidate (no parsing target, a target not free, not the chosen member) an **ignored** id; an id of Q with no candidate is decided by the ordinary rules. Neither set is counted by the preview, a converging id goes to `ApplyConvergence` instead of `ApplyOne`, an ignored id is decided as the plain `Ignore` (entry, tier, tags, text and row kept, no hold; its review items still follow the Part 3 and Part 4 reconcile rules), and `HoldIfUnprovenCandidate` returns at once for both, so a convergence that fails, is skipped by the scan or defers leaves the entry and its row for the next pull. **Fail closed, by the kind of pull.** A read the pre-pass cannot make (a W1 candidate's blob read that is not ok, a relevant W1 candidate whose local read or knowledge check cannot be made: unreadable, in two tiers, a corrupt knowledge row; a candidate canonical record that cannot be read; a target whose checks throw) ignores every id of Q in a **proven** pull (a target that cannot be checked is not free), which delays an ordinary deletion by one pull. In an **unproven** pull it ignores nothing for the ids it leaves uncleared (every id of Q for a failed W1 blob read, whose origin is unknown; else the ids that share the failed candidate's origin hash, whose lowest candidate cannot be read, or whose target cannot be checked), so the ordinary unproven hold (W6.5) applies to them: an ignore there would let `L` advance past the vanished record, and the next, proven pull would delete it without proof. The cleared ids keep their ignore in such a pull, and an id that would converge is ignored instead (an uncleared id may be the member that should converge); a held id later meets the ordinary rules (condition 7). An exception the pre-pass does not map ends the apply as `Failed("the alias rows could not be read: ...")` before anything is written. **The convergence (D3, D4, D5).** `ConvergeCore` re-reads `x` and the canonical id `c` (a change since the pre-pass defers), decides the canonical record against `x`'s entry with the unchanged no-base merge (`SyncMerge.decide` with row none, no pending or pushing stamps, no held item, the pull's proof; anything but an active `MergeGroups` fails), and hands it to the shared `PlanAndCarry`/`CarryOut` for `c` with `x`'s entry as the local view and `x`'s conflict item as `c`'s expected item. In **one `BEGIN IMMEDIATE` transaction**: `ConvergenceHolds` re-reads `x` (row, entry, pin items, conflict item, no held item) and that `c` is still free (else a deferral); `tx.RekeyMemory(tier, x, c)` moves the entry's row in place (`rekey-row`: only the id changes, so the rowid, vector, FTS row, tags, sticky flag, `access_count`, summary, source, metadata, decay score and timestamps stay; `rekey-parent`: every `parent_id` that names `x` in the six content tables; it refuses, writing nothing, when `x` is not in that tier or also in another table, or `c` is an id in any content table) and `GitSyncReviews.RekeyConflictItem(x, c)` moves `x`'s conflict item; then the ordinary re-read of `c`, store operations, row and item step run unchanged (so the pin and conflict items the no-base rules request are written by the existing arrival rules, after `x`'s re-keyed losers are reconciled against the applied text, and `ConflictItems.Append` is not used); `c`'s row is written with `x`'s `allowed_hash` (the `blocked_*` columns are left empty for the next scan); the `converge` step deletes `x`'s row, its `apply-failed` issue and its pin items, retargets `x`'s memory `import_log` rows to `c` (`RetargetImports`), writes the `git-sync` row for `c` with the origin hash, and marks the alias `(c, x)` `resolved` (`MarkResolved`, which inserts it for a detection with no row); it also writes, `INSERT OR IGNORE`, the `open` rows `(c, other)` that this pull's detections of `c` planned for the group's other local members still present (carried from the pre-pass in `ConvergeTarget.OtherRows`), because `c`'s own visit may defer or fail in that pull and once `c` exists here no detection runs again. A convergence that would write no row for `c` throws before anything of `x` is deleted. What carries, by the N-rules: equal content adopts `created_at`; a different text on an unpinned entry takes the canonical text and files the local text as a `conflict` item (NC4), on a pinned entry keeps the pin text and holds the canonical content as a `pin-edit` item (NC2); a project or scope difference alone takes the record's (NC3); the entry's pin stays (NS2, re-stamped) and a sticky canonical record raises a `new-pin` item (NS3); tags are the union and the tier the warmer (a local winner re-stamped). A convergence counts as `Updated`; a failure, skip or deferral is booked under `x` and the transaction rolls back. It also runs in an unproven pull: nothing is lost, and the return of `x`'s record is an alias skip. The ending is `resolved`, not `converged`, because this machine's own record of `x` is already gone. **Limits.** No background pass, no withhold rule (a non-canonical entry is still pushed) and no `abandoned` state: milestone 5. An open group whose canonical record is gone (or does not parse, or whose canonical id is taken here) stays open and its entry is kept; only one local member of a group converges and the others stay as they are. In a proven pull a W1 candidate that cannot be read makes the pre-pass ignore all of Q, so an ordinary remote deletion in that pull waits for the next one; in an unproven pull the ids it leaves uncleared are held instead (a person's question); nothing is lost. A locally deleted twin is not protected from a later insert of the other record. Neither the applier's alias code nor the store step names the cycle or the pusher (`GitSyncCycleCallerTests`). Tests: `SyncAliasTests.fs`, `GitSyncAliasesTests`, `GitSyncReviewsTests`, `SqliteStoreTransactionTests` (the re-key), `GitSyncApplierAliasSkipTests`, `GitSyncApplierConvergenceTests` and `AliasCycleTests` (whole cycles over `TwoMachineRig` with its third machine T: two legacy copies leave neither machine with a duplicate and one alias row each; T, which holds B's record as an entry, skips A's canonical record and, after B's record is removed by an ordinary commit, ends with one entry under the canonical id carrying its tier, tags and pin, with the differing local text in a `conflict` item or, under a local pin, the canonical text held as a `pin-edit`).

**Git sync review service (`GitSync/ReviewService*.cs`, `ApplyPlanning.cs`; rules in `Core/SyncMerge.fs` (`remoteDeletion`, `insertFrom`), `Core/SyncApply.fs` (`editedSinceHold`), `Core/SyncDeletion.fs` and `Core/SyncSetup.fs` (the refusals); milestone 1b-iii part 2, #162).** `ReviewService(ReviewEnvironment(Setup, Func<IEmbedder> Embedder, HotMaxContentChars, PinnedMaxContentChars))` answers this machine's held deletions (`held-delete` items) and, since Part 3 (#163), its pin items (see "Git sync pin review" below) one item at a time; the hidden `sync review` commands build it with `SyncSetupFactory.CreateReview`, and the `sync_review` tool of a later part will call it. There is no "all" in the service: the bulk forms are CLI loops over the single answers. `List()` opens the database read-only like `sync status` (`ReadOnlyDatabase`: no lock, no migration, nothing created) and returns the `open` and `approved` held deletions and the `open` and `unseen` pin items, ordinal by id, then kind; a held deletion comes with its state, direction, cause, shown hash (null for a remote hold), `arrivedAt` and the memory's text as data (the local entry's for a remote hold, the row's base's for a local one; control characters other than newline and tab, the line and paragraph separators U+2028 and U+2029 and the bidirectional format controls U+202A to U+202E and U+2066 to U+2069 removed, cut at `PinnedMaxContentChars` without splitting a surrogate pair, null when it cannot be read); no database file or no review table is an empty list, any other unreadable database (a pending write-ahead log included) is `ReviewListing.Failed`. `AcceptAsync(id, shownHash)` and `RestoreAsync(id, shownHash)` return a `SetupResult`: a settings load error is `failed` and a missing database file `no-held-item`, both before anything is created; then the sync directory is created when missing, the sync lock taken (`SyncLock`, 3 s; held: `busy`), `LegacyDatabaseProbe` run, the database opened read-write and migrated, the embedding of a local restore computed (the only work before the transaction; the embedder is created lazily, once, and an exception is `failed` with nothing written), and **one `BEGIN IMMEDIATE` transaction** (busy: `busy`) re-reads the item, the row and the entry, runs the checks and the answer, and commits only when the answer succeeds. **Check order** (`CheckItem`; each a refusal that changes nothing): an item `open` or `approved` (`no-held-item`); its row `active` with a base (`failed`: the row no longer matches the item); the entry read (`LocalEntryReader`: two tiers or unreadable is `unreadable-entry`); the entry present for a remote hold and absent for a local one (`stale-item`; the next pull closes the item); for a local hold (an approved item is one) the shown hash: none is `shown-hash-required`, one that differs from the item's current `record_hash` is `stale-item`, whose text ends with the item as it is now; for a remote `Accept` the edit test of D2 (`SyncApply.editedSinceHold`: the entry's content hash differs from `scanned_content_hash`, or a pending content stamp comes with a text that differs from the base's; `edited-locally`; a base that does not parse is `failed`). A remote hold ignores a hash. **Answers.** *Accept, remote hold* (any cause, a pinned entry included): `SyncMerge.remoteDeletion` (W6.4's decision), the apply's `tx.Delete` of the entry and its vector, the row `BuildRow` plans for that decision (`forgotten`, base kept, pending stamps, `pushing_stamps` and `repush_groups` cleared), the item removed, and a `pending-changes-dropped` note line when a tag, tier, project, scope or type change went with it; no guard counts it. *Accept, local hold*: the item becomes `approved` (`GitSyncReviews.ApproveHeld`; direction, hash and cause kept) and nothing else is written; an already approved item answers `already accepted`. The next pull decides it as a proven `PushDeletion` that the guard does not count while the record's blob id equals the item's hash (else it re-opens the item with the new hash), and the push removes the record; `GitSyncPusher.Finalize`'s `Forget` removes the item, before its early return for a row that is no longer `active` (see "Git sync pull", approved items). *Restore, remote hold*: the entry and its pin stay as they are; the row is rewritten as a new one (no base, one fresh stamp per group from `ApplyPlanning.IssueStamp` with that group's stamp in the old base as the floor, so a machine with a skewed clock never sees the new record as older; `pushing_stamps` and `repush_groups` cleared; the comparison columns kept) and the item removed, so the next push writes a new record (a sticky one for a pinned entry). A base that does not parse, or no stamp to issue (no sync identity, or the clock range is exhausted), is `failed`. A machine that kept the old base takes the new record as an update; one that already forgot the memory applies W3 and does not resurrect it while the text is the same (the documented limit of the umbrella's "same-text restore"). *Restore, local hold* (an approved item too): the memory is inserted again from the row's base as the apply inserts a record (`SyncMerge.insertFrom(record, false)`, `ApplyPlanning.PlanStore`/`InsertRecord`/`BuildRow`/`LogImport`: the record's tier, or warm when `SyncApply.demotesToWarm` applies, the same id, the embedding, the `import_log` row) but **never sticky**; inside the transaction the base must still be the one embedded and no knowledge entry may hold the id (`stale-item`), and a base that does not parse is `failed`. The row is the one the apply writes for `InsertFromRecord` (pending stamps cleared, comparison columns from the stored entry, so `local_sticky` is false and the next push writes nothing: **no unpin is pushed**). A sticky base opens a `new-pin` item (`GitSyncReviews.UpsertPinItem`, upsert on `(entry_id, kind)`, state `open`, `record_hash` = the shown hash (`SyncPin.shownHash`) of the text, project and scope of the entry it re-inserted, `machine` = the base record's `written_by`, payload `{"origin":"restore"}`), answered like any pin item; the held item is removed. **What the answers rely on in the pull (D4, D10)**: the `approved` state (`GitSyncReviews.ReadOpenHeld` still reads only `open`, so the push's held exclusion and the existing readers are unchanged and an approved id is not excluded; `ReadApprovedHeld` feeds the applier's shared `Decide`); the **refreshed hash** (an open local item the pull leaves open has its `record_hash` set to the record's current blob id, so the shown-hash check compares with the record as of the last pull, not the clone's `HEAD`, which after a rejected push is an unpublished commit); the **visit set** (every id with a `held-delete` item, open or approved, is visited, so an entry re-created under its `active` row closes an open local item or removes an approved one instead of leaving it unanswerable or pre-approving a later deletion). Known limit: the stale reference of a held local deletion is the item's own hash, which only a pull refreshes, so a local hold restored after another machine already removed the record, and before this machine pulled, leaves the restored entry to the next proven pull's remote deletion (W6.4, counted by the guard); the person re-creates the memory after that sync (a pinned entry or an unproven pull is held instead, W6.2 or W6.5, so the limit is that of the non-sticky, proven case). **`ApplyPlanning`** (internal static: `PlanStore`, `BuildRow`, `ParseBase`, `InKnowledge`, `InsertRecord`, `LogImport`, `IssueStamp` with the clock as a parameter; pin review added `RecordContent`, `ExpectedEntry`, `PlaceholderIssue`, `WriteStore`, `ApplyBaseContent` and `WithComparison`) is the apply's row and insert planning, moved from `GitSyncApplier.Entry.cs` unchanged in behaviour so the applier and the service write the same rows, inserts, stamps and import-log lines from one copy. The service leaves work for the next cycle only through the rows and items it writes and names neither the cycle nor the pusher (`GitSyncCycleCallerTests`). Test seams: `AfterOpen`, `BeforeTransaction`, `BeforeStep` (a remote `Accept`'s store steps and its `row` step), `CheckForTestsAsync` (every check in a transaction that is rolled back), `EmbedderCreations`. Tests: `ReviewServiceTests`, `ReviewServiceAcceptTests`, `ReviewServiceRestoreTests` (over `ApplyRig`, with `ReviewServices.For` and `ReviewHolds` in `ReviewTestSupport.cs`) and `ReviewServiceCycleTests` (whole cycles over `CycleRig` and `TwoMachineRig`: an accepted local hold removed by a proven cycle, also with more approved items than the guard's limit; a restored remote hold published as a new record, sticky for a pin, reaching a machine that never forgot it and not resurrecting it on one that did; a restored local hold of a pin pushing no unpin).

**Git sync pin review (`GitSync/PinPlanning.cs`, the pin step of `GitSyncApplier.Entry.cs`, `ReviewService.Pins.cs`, `ReviewService.List.cs`, the pin members of `GitSyncReviews.cs`; rules in `Core/SyncPin.fs`, refusals in `Core/SyncSetup.fs`; milestone 1b-iii part 3, #163).** A pin that arrives from the repository never takes effect until the person approves it, and an edit that arrives for a memory pinned here is held until the person decides. **Items and states.** Two kinds of `git_sync_review` row, keyed `(entry_id, kind)` (no schema change): `new-pin` (a record pins an entry that is not pinned here) and `pin-edit` (a held remote edit of an entry pinned here). `direction` NULL, `machine` the record's `written_by`, `arrived_at` the applier clock, `payload_json` `{}` (pull) or `{"origin":"restore"}` (Part 2's restore of a sticky local hold). States `open`, `unseen` (what the item shows changed since it was shown; every reader treats it as open: it is answerable, listed, visited and blocks what an open item blocks), `approved` and `declined` (answered; such an item stays until a new arrival or a removal rule). **The shown hash** (`SyncPin.shownHash text project scope`: SHA-256 over `total-recall/review/pin/v1\n` and the three fields, each written as a presence byte, a 4-byte big-endian length and the UTF-8 bytes, so `None` and `""` differ) is an item's `record_hash`, always of the state after the pull's decision: a `new-pin` shows the **stored entry's** text, project and scope (what `approve` would pin), a `pin-edit` the **post-decision base's** content group (the held record) **as the store reads it back** (an empty project or scope is none, because applying the base stores `""` and the entry reads it as none; `ApplyPlanning.BaseShownHash` is the one place it is computed, for the arrival, the reconcile's base view, the list and the stale check, so an approved item closes by pin-edit rule 2). The CLI header of a pin item also shows when it arrived (`from <machine|-> arrived <UTC ISO-8601 to the second> project ...`). A tag, tier or stamp change never makes an answer stale. **Arrival (D3).** A `NewPin` or `PinEdit` decision is carried out as for any entry (no decision postpones): an insert from a sticky record (W1, W3, W8.1, Part 2's restore) inserts an ordinary entry (`InsertEntryOpts` has no sticky field) in the tier the apply chooses (hot; warm over `tiers.hot.max_content_chars`, and `approve` moves it to hot), FS4, FS7 and NS3 keep the entry unpinned and apply the other groups, FC2 and NC2 hold the content group (no content update, tags and tier still apply, the base's content group advances to the record's and a pending content stamp is cleared). Then, in the entry's transaction, after the reconcile below, `SyncPin.arrival` runs for each request the decision carried (`PinPlanning.Requests`): no item, or an answered one, writes it `open` with the hash and the record's machine; an `open` or `unseen` one with the same hash is left; with another hash it becomes `unseen` with the new hash. After the carried-out decision the base equals the record, so a repeated pull raises nothing and is a no-op (no transaction). **Reconcile (D4)**, `SyncPin.reconcile`, first match, per kind, on the post-decision state (the stored entry, the row, its base, whether the record is present). `new-pin`: (1) entry absent or row not `active`: remove; (2) entry sticky (pinned here, or approved and in effect): remove; (3) record absent or the post-decision base not sticky (a remote unpin or removal; a record that only regressed to non-sticky while the base keeps the pin does not count): remove; (4) `open`/`unseen` and the entry's shown hash differs: `unseen` with the new hash; (5) keep (a declined item is not re-asked by a text change, only by a new pin). `pin-edit`: (1) entry absent, or row not `active` or without a base: remove; (2) entry's shown hash equals the base's (nothing is held any more: the apply took the record's content, the held text came to equal the pin text, or an approval is in effect): remove; (3) the entry was edited here since the item arrived (a pending content stamp, or `SyncScan.contentHash` of the entry differs from `scanned_content_hash`): remove, and the local edit meets the record as an ordinary pending change, so any local text, project or scope edit re-asserts the local content group when pushed (this is also what removes a declined item); a tag or tier edit does not close it; (4) entry not sticky (unpinned here, or a remote unpin applied): **apply the base's content group (D5)**, then remove; (5) `open`/`unseen` and the base's shown hash differs: `unseen` with the new hash; (6) keep (a record that is absent while the entry stays pinned is a held deletion; the item is unchanged). Every update to `unseen` also rewrites `machine` (the record's `written_by`). Known limit: the items of an id are reconciled in kind order, so when a `new-pin` and a `pin-edit` item of one id exist and pin-edit rule 4 applies the held content in the same plan, the `new-pin` item is checked against the entry before that content is applied and can be marked `unseen` with an out-of-date hash; a pull does not leave both kinds on one id and the next pull corrects the hash, so this is accepted. `ApplyDrop` deletes the id's pin items in its own transaction (`pins` step). **When it runs.** `PinPlanning.Plan` (the reconcile of every item of the id, then the arrivals over what the reconcile left; a `PinPlan` of ordered `PinWrite`s and the `base_json` to apply, if any) runs **before** `BEGIN IMMEDIATE`, only when the id has an item or the decision a pin request, on the **expected** post-decision state: `ApplyPlanning.ExpectedEntry` (the entry as the plan's store operations will leave it) and the row `BuildRow` plans with `ApplyPlanning.PlaceholderIssue` (a dummy stamp, read only as present or absent, so a restamp or a fresh content stamp is planned, not failed). A non-empty plan counts as a change for the no-op shortcut, and when pin-edit rule 4 will apply a base whose text differs from the expected entry's, that text is embedded before the transaction. Inside the transaction (`pins` step, after the row write) the plan is recomputed from the re-read state; a plan that differs (`PinPlan.Matches`), or a vector that no longer fits whether the text changes, **defers** the entry; the items read before the transaction are also compared at the re-read. **D5, a local unpin applies the held edit.** `ApplyPlanning.ApplyBaseContent` writes to the entry exactly what `TakeTheirs` writes for the base's content group (text, project or clear, scope, entry type, source or clear, `created_at`), with the vector of the base's text (none when the text is unchanged) and `TakeTheirs`' tier rule (over the hot limit it goes warm, and a pending tier stamp the colder tier no longer beats the base's with is dropped); `WithComparison` records the row's comparison columns from the stored entry; no content stamp is issued (the content equals the record's), and a pending unpin push is unaffected. **The answers (D6, D7)**, `ReviewService.ApproveAsync(id, kind, shownHash)` and `DeclineAsync(id, kind, shownHash)`, in the held-deletion frame (`RunAsync`: settings, the sync lock, the legacy probe, migrations, one `BEGIN IMMEDIATE`) with `CheckPin`, in this order: an item of the kind `open` or `unseen` (`no-pin-item`, also for an unknown kind); the row `active` with a base and the entry read (`ReadRowAndEntry`: `failed`, `unreadable-entry`; a base that does not parse is `failed`); a shown hash (`shown-hash-required`, for both verbs); the entry present and not sticky for a `new-pin`, sticky for a `pin-edit` (`stale-item`, nothing written: the next pull closes the item); for a `pin-edit`, no local content edit (a pending content stamp or `contentHash` against `scanned_content_hash`: `edited-locally`); the shown hash equal to the live one (else `stale-item` with what the item shows now, and the service **commits** the item's update to the live hash, `unseen` and the base's `written_by` as machine: `CheckOutcome.CommitRefusal`, the one refusal that writes); for `approve` only, the text, project and scope unchanged by the list's sanitiser (`unshowable-text`) and the text within `tiers.pinned.max_content_chars` (0 or less: 500; `over-pin-cap`, worded by `PinnedTierLimits.ContentLimitMessage`). *Approve `new-pin`*: `Move` to hot when not there, sticky, `decay_score` 1.0, the row with `local_sticky` true, `local_tier` hot and no pending sticky stamp (the base already holds the pin), item `approved`; nothing is pushed, and the next pull removes the item (new-pin rule 2). *Approve `pin-edit`*: the base's text is embedded before the transaction (`EmbedPinBase`) and checked against the row's `base_json` inside it (a change is `stale-item`), then `ApplyBaseContent` and `WithComparison` as in D5 (the entry stays pinned), item `approved`; nothing is pushed. *Decline `new-pin`*: only the item changes (`declined`); the record is left alone, so the pin stays on the other machines. *Decline `pin-edit`*: a content stamp issued above the base's content stamp (`IssueStamp`; none to issue: `failed`) is left pending, item `declined`, and the answer carries `ReviewService.RevertWarning`; the next pull removes the item (pin-edit rule 3) and the push writes the local content group as an ordinary change, through its own secret re-check. Fault seam `BeforeStep`: the store steps, `row`, `resolve` (the last write). **List and CLI.** `List()` shows an open or unseen pin item with its kind, state, live shown hash, machine, project and scope (`ShownField`: the text rules, newlines and tabs replaced, 200 characters), the text at the pinned cap (`new-pin`: the entry's, source `local entry`; `pin-edit`: the base's, source `repository record`, with `CurrentText`, the pinned text here). The hidden `sync review approve|decline <id> --shown <hash>` (`ReviewCommand`) requires `--shown` (8 or more hex digits, a prefix of the item's hash; usage error, exit 2, without it), resolves the item by `(id, kind)` from the listing (none: `no-pin-item`; two pin items: `stale-item`, "run a sync first") and prints the revert warning before it declines a `pin-edit`; `accept`/`restore` and the bulk forms answer held deletions only, and there is no bulk form for pins. Tests: `SyncPinTests.fs`, `GitSyncApplierPinReviewTests`, `ReviewServicePinTests`, `GitSyncReviewsTests`, `SyncCommandTests` and `PinReviewCycleTests` (whole cycles over `TwoMachineRig`: a pin from A is an ordinary hot entry on B with an open item and a complete cycle; approve pushes nothing; decline never unpins A; a local pin closes the item and pushes as an ordinary pin; a tag edit while an edit is held pushes only the tags; approving a held edit pushes nothing; declining it pushes B's text, which A then takes as an ordinary edit (a machine that has pinned the memory holds it as an edit instead), and a token in that text is held back by the push's secret check; a local unpin applies the held edit and pushes only the unpin; a local text or project edit pushes B's content group; a new pin that is also a conflict is carried out with both items and the cycle completes).

**Git sync scan (`GitSync/GitSyncScanner*.cs`, `GitSyncRows.cs`; rules in `Core/SyncScan.fs`).** `new GitSyncScanner(connection, nowMs).Scan()` returns `ScanOutcome`: `Done(ScanSummary)`, `NotJoined` (no valid `git_sync_machine`) or `Failed(reason)`. It reads inside **one** read transaction (raw `BEGIN`, first `SELECT` starts the WAL snapshot: the machine id, the clock and warning keys, every `git_sync_entry` row, the `ineligible-id` issues, the hot, warm and cold memory tables, the knowledge ids), decides per id with `SyncScan.decide` in ordinal id order, and writes in **one** `BEGIN IMMEDIATE` transaction (rows, issues, clock, warning). A scan with nothing to write opens no write transaction; two scans in a row with no edit change nothing. It takes no lock, runs no `git`, uses no network and writes only `git_sync_entry`, `git_sync_issue` and the `_meta` keys `git_sync_hlc` and `git_sync_clock_warning` (and removes the `held-delete` item of a row it moves to `left` or reactivates, in the same transaction, so the item cannot outlive the base it was opened for; milestone 1b-ii), never a memory, knowledge, vector, `import_log` or `compaction_log` row. Per group it stamps content (text, project, scope, entry type, source tool, `created_at`), sticky (a pin or unpin) and tier (only a warmer tier; demotion just updates `local_tier`); a tags change updates the tags hash and issues no stamp. Stamps come from `Clock.issue` with the greater of the group's base stamp (read from `base_json`) and its pending stamp as the floor; `Clock.guardStartup` runs once per scan. An id in two tiers, an unreadable entry and an ineligible id are skipped (listed in `Skipped` or `Ineligible`, and never treated as deleted); a group whose clock is exhausted is skipped and retried next scan. An active row whose memory exists nowhere is only **reported** in `LocalDeletions` (with has-base and has-pushing-stamps flags); the scan never drops, forgets or deletes it (1b-ii acts on it); a retype to knowledge moves the row to `left`. Internal test seams: `AfterFirstTableRead`, `BeforeWrite(step)`, `WriteTransactionCount`. What the scan requires of the later parts: the apply sets `scanned_content_hash`, `scanned_tags_hash`, `local_sticky` and `local_tier` from the stored entry after its own write (or the next scan reads the pulled change as a local edit), reaches rows with no base and no entry whose id is absent from the repository, and exempts groups the scan skipped; the push and the apply clear the pending stamps. A stamp column that does not parse reads as none and is written back as NULL when the row is rewritten. **Secret block (milestone 1b-iii part 1, #161, spec D1 to D4, D9, D10).** After the plan is built and before the write transaction, `ApplySecretPass` (`GitSyncScanner.Secrets.cs`) evaluates every eligible entry whose row the plan will write or whose stored row is `active` (skipped and ineligible ids, and `forgotten`/`left` rows without an entry, are not evaluated), so an entry the plan calls `NoChange` is still checked when its key matches neither stored key. The key is `SyncSecret.secretKey` (text, project, scope and normalised tags in one hash); `SyncSecret.precheck` skips the detectors for an allowed (`allowed_hash` = key) or still-blocked (`secret-detected` with `blocked_hash` = key) entry, and otherwise `SecretDetector` (test seam; default `SensitiveContentScanner.ScanSecrets`, the Token and PrivateKey detectors only, so `git@github.com` and plain addresses such as `noreply@example.com` are not blocked) runs over the text, project, scope and each tag. A hit writes `blocked_reason = 'secret-detected'` and `blocked_hash` = the key, replacing any writer reason (such as `too-large`, which the next push re-marks after a clean re-scan lifts the secret mark); no hit lifts a secret mark and keeps any other reason; an allowed entry clears a secret mark. The pass edits the row the plan already holds, so one id gives one row write; `allowed_hash` is never written by the scan (only `FreshRow` starts a new or reactivated row with all three columns empty). `ScanSummary.Blocked` lists the ids on whose changed row the scan set the block (including a block re-stamped under a new key) and `Unblocked` the ids whose secret block was lifted, either by a clean re-scan or because the user allowed the current fields (the `afterAllowed` path of `ApplySecretPass` adds those ids too). The field-set check itself (the text, project, scope and each tag run through `SecretDetector`) is `GitSync/SecretFields.cs`, shared by this pass and the push preparation. Reasons are category labels (`API token or secret`, `private key block`, `scan timed out`); nothing stores, logs or prints a matched value. **The detector (`Eval/SensitiveContentScanner.cs`, spec D9)** is the union of `Redact`'s token patterns and private-key begin line (a PGP `PRIVATE KEY BLOCK` included), reused from `RedactionPatterns`, and its own earlier patterns kept as legacy entries (the unbounded `sk-[A-Za-z0-9]{16,}`, which also holds back text such as `mask-abcdefghijklmnopqrst`, and `-----BEGIN [A-Z ]*PRIVATE KEY-----`); `Redact` itself, its output and `RedactionVersion` are unchanged. Every pattern is matched with a 1 s timeout (`SecretScanTimeout`; an internal overload takes the bound for tests), and a timeout is a hit (`scan timed out`, fail closed) in `ScanSecrets` and in `Scan`, so `eval_grow`'s accept guard fails closed too. **Cost (D10).** No marker is stored: every scan runs the detectors on each eligible active entry whose key matches neither `blocked_hash` nor `allowed_hash`, which in the common case (a clean entry) is every active entry once per cycle; an entry blocked and unchanged, or allowed and unchanged, is skipped. The work is linear in the text and bounded per pattern by the timeout. Measured for #161 (Linux, Intel Core i5-14500, Debug test build, one throwaway run of three passes, not a committed test): one scan pass over 10,000 clean active entries of 2,000 characters each, with nothing changed since the previous scan, took 350 to 460 ms, of which the detectors took 25 to 29 ms over the 10,000 calls; the first scan of that store (creating every row) took about 1.0 s. Memory text has no single size cap (`memory_store` allows 100,000 characters, other paths none); an entry over the writer's limit is `too-large` for the push anyway.

**Git sync guards (`GitSync/RepoGuard*.cs`, `ManifestFile.cs`, `HostIdentity.cs`, `GitSyncIdentityStore.cs`, `PublicRepoProbe.cs`).**
`RepoGuard.EvaluateIdentityAsync(revision = Head)` reads the settings, the stored identity (`_meta` keys `git_sync_remote`,
`git_sync_repo_id`, `git_sync_host`), the host fingerprint and the repository's manifest from the **local clone** at the given
revision (the cycle passes `refs/remotes/origin/<branch>` after its fetch, when `HEAD` is still the old commit) and returns a
`GuardVerdict`: the `Core.SyncIdentity.JoinState`, the `ManifestRead` outcome (`NoClone` = no `.git` under the clone directory,
`NoManifest`, `Invalid`, `Unreadable` for any git failure or a blob over 64 KiB, `Newer`, `Ok`) and `HostUnverified`.
`GuardVerdict.CanSync` is true only when joined, the host fingerprint was available and the manifest is `Ok` or there is no
clone yet; a caller reports a newer format before `not-joined`. It runs no network command (`Clone`, `LsRemote`, `Fetch`,
`Push`). `ManifestFile.Parse` lets a newer `format` win over every refusal except non-JSON and invalid UTF-8 (a strict UTF-8
check first, then a permissive look for the first root `format`), then applies the 4 KiB cap and the `v1` rules, and never
throws on hostile input. `HostIdentity` hashes the OS machine id (Linux `/etc/machine-id`, macOS `ioreg`, Windows `MachineGuid`)
with the canonical database path (links resolved one hop at a time, `\\?\` stripped, lower-cased on Windows and macOS);
a source that exists but fails makes the fingerprint unavailable (`null`) instead of reading as a moved directory.
`RepoGuard.CheckPublicAsync` asks `GET https://api.github.com/repos/<owner>/<repo>` with no credentials, no cookies, at most 3
redirects and a 5-second limit (only an answer from the base address's host counts): 200 is public (refused), 404 private (cached
24 hours in `_meta.git_sync_public_check`; nothing else is cached, and a store fault on the cache is a miss), anything else is
unknown (one warning per guard); a non-GitHub remote is skipped with one notice. There is no in-process memo of the verdict.
`ServerComposition.OpenGit` (the `git` storage mode) validates the remote, the branch and that a `git` executable is on the
`PATH` (`GitExecutable.TryFind`, no process) and otherwise opens the plain local store with the label `git`; a failure falls back
to `sqlite (git failed)`.

**Sync-on-read and the current session.** `Transcripts/CurrentSession.cs` (`CurrentKind` `None`/`Marker`/`Guessed`, wire words `none`/`marker`/`guessed`), `ProcessAncestry.cs` (`Chain()`: at most 12 ancestors, nearest first, excluding the engine; Linux reads field 4 of `/proc/<pid>/stat` after the last `)`, macOS runs `ps -o ppid= -p <pid>` with 1 s per hop or the time left of 3 s in all, any other platform gives an empty list; `Walk()` also says whether the walk ended normally (pid 1, a repeat, 12 hops) or on a failed read or the time limit, and `CachedAncestry` keeps only a non-empty, normally ended chain for the life of the process), `LiveSessionFinder.cs` (reads `<dataDir>/live/<host>-<pid>.json` for each ancestor and adapter, nearest first, and accepts a marker only if it passes the shape, name, session-id, path-layout (exactly two components under the adapter's root, none a link, no `.` or `..`) and process-start checks; a refusal is skipped and logged once per file) and `TranscriptSyncService.cs` (`ITranscriptSync.SyncCurrent(embed, ct)` returns `SyncResult(Current, Complete, Note, ProjectKey)` and never throws except for the caller's cancellation). A sync: waits for a running one (at most the ingest budget), finds the session (marker, else the newest Claude Code session file written within 30 minutes: `Guessed`), opens the archive with `TranscriptStore.Open(location, create: false, busyTimeoutMs: 500)`, ingests the session's file through `TranscriptIngester.IngestSession` under a 2 s budget (so forgotten sessions, projects, roots and the cutoff are excluded by the same code as the pass and `backfill`), and, only when the caller passes a `SyncEmbedPlan` (search), runs `TranscriptEmbedWorker.Run` once with `EmbedBudget(2 s, 8)`, `preferSession` set and `recordRun: false`, behind the gate `TranscriptSearchService.BuildEmbedGate` builds (the pass's gate, `ServerPass: true`). The service is built by `ServerComposition` per composition without I/O and reached by the three transcript handlers through `TranscriptSyncCall`; `ArchivePassOptions.Sync` (`TranscriptSyncOptions`) carries its test seams (ancestors, data directory, process start, adapters, clock, store open, embedder). The embed queue takes an optional session preference: `ITranscriptStore.NextEmbedWork(limit, exclude, preferSession)` reads that session's waiting chunks first and fills the rest from the whole queue excluding the ids already returned; `SqliteConnection.Open` and `TranscriptStore.Open` take an optional busy timeout (Microsoft.Data.Sqlite also keeps a whole-second command timeout, so a held write lock made a sync call wait about 1.2 s in the measurement). Nothing here touches the schema. The hook side is `hooks/live-marker/`; see the root `AGENTS.md` and `docs/transcripts.md#keeping-the-current-session-up-to-date`.

**Git sync transport (`GitSync/GitProcess.cs`, `GitClient*.cs`, `GitSyncPaths.cs`, `SyncLock.cs`).** Every git call is one
of the closed `Core.SyncGit.GitCommand` cases (no case can force, delete or mirror; a recording `IGitProcess` plus
`ForceFlags.AssertNone` checks every argument list the tests produce). `GitProcess` is the only place a process starts:
no shell, argument list from `SyncGit.build`, the `GIT_*` environment scrubbed to an allow-list, a hard kill of the
process tree at the call's limit or cancellation, bounded output, and standard error redacted as it is read (a
credential or a UTF-8 character split across reads is never redacted in pieces). `GitClient` types the operations
(version, init, clone, ls-remote, fetch, reset, clean, ancestry, rev-parse, the protective ref, stale locks, ls-tree,
diff-tree, cat-file, stage, stage-paths, staged-set, commit, push; `stage` is `add -A -f` so a remote's `.gitignore` cannot drop a record); a clone-scoped command carries `--git-dir`/`--work-tree` so a damaged clone
can never make git act on an enclosing repository, and every call sets `GIT_CEILING_DIRECTORIES` to the database's
directory (a database directory whose path contains the path-list separator, `:` on Unix, therefore fails every call but
the version check). The user's ssh command (the process's `GIT_SSH_COMMAND`, else `core.sshCommand` as git resolves it:
system, global and XDG files with includes, read from the sync directory under the ceiling; once per client) is passed on as `GIT_SSH_COMMAND` with
`-o BatchMode=yes -o ConnectTimeout=8` appended (`-batch` for a plink or putty program; the variable is left alone when
only `GIT_SSH` is set, since such a program takes no OpenSSH options). The layout is
`<directory of the database file>/sync/<dbKey>/{lock, no-hooks, empty, <cloneKey>/repo}` where `dbKey` is the first 12 hex of
the SHA-256 of the database file's *name* (lower-cased on Windows and macOS), so two databases in one directory never
share a clone, a protective ref or a lock. `SyncLock` is a file opened with `FileShare.None` (released by the operating
system if the holder dies; the file is never deleted and holds no text); it throws `NotSupportedException` when .NET's
file locking is disabled (`DOTNET_SYSTEM_IO_DISABLEFILELOCKING` is `1` or `true`, or the `System.IO.DisableFileLocking`
switch is set) and tells "busy" (a sharing violation, or EAGAIN) from a real error. .NET ignores a flock failure other than
"would block", so on a file system without flock support the lock excludes no one. The tests that need `git` are
`[GitFact]`, the ones that need `sh` are `[ShFact]`, the ones that need both are `[GitShFact]` and the one that needs
`flock(1)` is `[FlockFact]`: they are ordinary tests (not `Integration`), so the standard verify runs them and a missing
tool shows as skips. Windows runs the `[GitFact]` tests and skips the `sh`, `git`+`sh` and `flock` ones.

Known limits, left to later milestones: a failed or interrupted `CloneAsync` can leave a partial clone directory that the
caller must move aside; a remote can send a very large blob or pack (only the call's timeout bounds clone and fetch); and
a remote's `.gitattributes` can select a filter driver the user's own configuration defines (the repository is the
user's own, and the filter is theirs).

**Git sync setup commands (`GitSync/SyncSetupService*.cs`, `Cli/Commands/Sync/`).** `total-recall sync init --url <repo> [--branch <b>]`, `sync join <repo> [--branch <b>]`, `sync leave`, `sync status`, `sync unblock <id>` and `sync review` (`list`, `accept <id> [--shown <hash>]`, `restore <id> [--shown <hash>]`, `accept-deletions --all`, `restore-deletions --all`; `Cli/Commands/Sync/ReviewCommand.cs` over the review service, see "Git sync review service"; the bulk forms run only when standard input and output are both a terminal) are **hidden** until milestone 1b-iii (`ICliCommand.Hidden`: the top-level help leaves them out and no document, help text or `config set` refusal names them; `HiddenCommandTests` scans for that). The pure rules are `Core/SyncSetup.fs`; the service does the I/O. `init` and `join` refuse on Cortex or Postgres (the user sets `storage.mode = "local"` by hand first) and on an address holding a credential. Recording is ordered so that a crash is repaired by running the command again: place the clone (a new one, or the earlier one moved aside), then ONE database transaction (identity and `_meta` keys; `ClearForNewRepository` only when the repository differs), then the `config.toml` write (`storage.mode = "git"` and `[git_sync]`; `config.toml` is rewritten **without comments**, as `config set` does). A clone is never deleted: `CloneSideline.Move` renames it to `repo.<label>-<time>` (`unpushed`, `broken`, `left`, `superseded`) and the commands print where it went. A `join` that finds a clone refreshes it (fetch, then `reset --hard` to the remote branch, never `clean`); a clone git cannot read is sidelined as `broken`, and a fetch failure of kind `Other` is probed locally first (Interpretation 13 of the plan). `init` and `join` open the database with `SqliteConnection.Open(path, pooling:false)` plus `RunMigrations` and a borrowed `SqliteStore`; `LegacyDatabaseProbe` refuses a database of an older format first. `status` is read-only and creates nothing: it opens the database read-only (`ReadOnlyDatabase`, `ReadOnlyMeta`: an immutable URI when no `-wal`/`-shm` sidecar exists, `Mode=ReadOnly` when both do, and nothing when exactly one does), reads the manifest only when the `no-hooks` directory and `empty` file already exist, and never touches the network. Its `blocked` section (#161, spec D8), printed right before the final `last sync` line, comes from `SyncSetupService.ReadBlocked` on the same read-only connection: one statement over `git_sync_entry` for `state = 'active'` rows with a non-null `blocked_reason` (a `forgotten` or `left` row that kept its columns is not listed, and a state this build does not know is simply not matched, because the columns are read directly and never through `GitSyncRows.ReadAll`), at most 20 `(id, reason)` pairs ordered by `entry_id` (binary, i.e. ordinal) plus a `count(*) OVER ()` total, then `  and N more`; every reason is listed (a writer's `too-large` as well as `secret-detected`). It takes no lock and creates nothing; no `git_sync_entry` table (an unmigrated database) or a read error prints `blocked: unknown (<reason>)`, as do a settings load error and a database `ReadOnlyDatabase` will not open (with their reason), and `blocked: unknown (no database)` only when the database file does not exist. **`sync unblock <id>`** (`SyncSetupService.Unblock.cs`, `Cli/Commands/Sync/UnblockCommand.cs`; #161, spec D7) releases a memory held back by a secret: it refuses a missing database as `unknown-entry` before opening or creating anything, a missing sync directory (no cycle ever ran on this database, or the directory was removed) is refused as `not-blocked` with its own text ("no sync has run on this database (there is no sync directory), so nothing is blocked; nothing changed"), before anything is created or locked (if a row still lists the memory as blocked, run `sync join` or `sync leave` or a later `sync now` first to recreate the directory), then it takes the sync lock (`busy` when held, or when the database is busy), opens the database read-write with migrations as `init` does, and in one immediate transaction reads the entry (`LocalEntryReader.Read`: absent is `unknown-entry`, in two tiers or unreadable is `unreadable-entry`), then the row (none, not `active`, or a reason other than `secret-detected` is `not-blocked`), then compares the current `SyncSecret.secretKey` with `blocked_hash` (different is `changed-since-blocked`: the fields changed after the block and the user was not shown them), and writes `allowed_hash` = the key with the mark cleared. After the commit it runs the detector on the content it read and prints `unblocked <id>` and the categories found, never a value. A later change to any of the four fields changes the key, so the entry is checked again. **A release is per machine**: `allowed_hash` is local state and is never synced, so another machine that pulls the released memory checks it there, and its own later changes to it are held until it is released there as well. Neither `unblock` nor `status` names the cycle or the pusher (`GitSyncCycleCallerTests`). Results go to standard output, notices and git progress to standard error, then `refused: <name>: <text>` and `note:` lines; exit 0 done, 1 refused or failed, 2 usage. Tests: `SyncSetup*Tests` (Infrastructure, `SetupRig` and `BareRemote` in `SyncSetupTestSupport.cs`) and `SyncCommandTests` (Cli, end to end with git and the data directory redirected).

**Borrowed-connection pattern**: `SqliteStore` accepts a `SqliteConnection` and does NOT dispose it.
The process-lifetime connection is owned by `ServerComposition.OpenSqlite()` → `ServerCompositionHandles`.

### Backend Selection

`ServerComposition.OpenProduction()` reads `[storage] mode` from config:
- `"local"` (default) → `SqliteStore` + `VectorSearch` (sqlite-vec)
- `"postgres"` → `PostgresStore` + `PgvectorSearch`
- `"cortex"` → `RoutingStore` wrapping `SqliteStore` + `CortexClient` for bidirectional sync

**Fallback**: If Cortex/Postgres fails to open, the composition root catches the exception and
falls back to SQLite, setting `StorageMode` to `"sqlite (cortex failed)"`.

**The transcript archive has its own migration chain.** `Storage/TranscriptSchema.cs` holds `TranscriptMigrationRunner` (internal), with its own `Migrations[]` and its own `tx_schema_version` table. It mirrors `RunMigrations` (one transaction, applies the versions above `MAX(version)`, idempotent) but writes no `_meta` marker and never touches `MigrationRunner`, so the main chain stays at 18 and `SchemaTests` / `GitSyncSchemaTests` are unchanged. Migration 3 adds the vec0 table `tx_chunk_vec` (rowid = `tx_chunk.id`; metadata columns `session_id`, `project`, `kind`, `ts`, 384-float cosine embedding; no partition key, so `reproject` can rewrite the project), the triggers that delete a chunk's vector when the chunk is deleted or its `content` changes and that carry a session's kind or project change into the vectors, narrows the text-index update trigger to `UPDATE OF content`, adds `tx_chunk.embed_attempts` and the partial index `idx_tx_chunk_unembedded`, and resets `embedded` to 0 (no vector existed). It needs the vec0 extension on the connection that opens the archive. The archive's embedder fingerprint and lease live in `tx_state` (`embed.provider|model|revision|dimensions`, `embed.lease`, `embed.last_run`). Migration 2 adds to `tx_session` the columns `settled_user_turns` (real user turns before the watermark), `built_under_cutoff` (the forget-everything cutoff the stored pass was built under, as text) and `project_root` (the repository directory the project is excluded under) and the index `idx_tx_session_project_kind` on `(project_key, kind)`. Migration 1 creates `tx_session`, `tx_chunk`, the FTS5 table `tx_chunk_fts` (external content, with the secure-delete option on), `tx_forgotten`, `tx_state` and `tx_schema_version`. The archive tables live in the main database or in the file `transcripts.db_path` names; `Transcripts/TranscriptStore.cs` owns its connection and decides which. Do not add archive tables to `MigrationRunner`, and do not mention `tx_`, `Transcript` or `Archive` under `Sync/`, `GitSync/` or the Core sync modules (a test pins it). See `docs/transcripts.md`.

**Reading the archive.** `Transcripts/TranscriptReadService.cs` (`Get`, `Sessions`) is the read side of `transcript_get` and `transcript_sessions`. It takes a `TranscriptLocation` only (no settings, no embedder, no provider), opens the archive per call with `TranscriptStore.Open(location, create: false)`, reads inside one deferred read transaction, `ITranscriptStore.BeginReads()` (`Transcripts/TranscriptReads.cs`, `ITranscriptReads`: `AnyChunk`, `SessionByRef`, `SessionById`, `ChunkById`, `ChunksOfExchange`, `ExchangesInRange`, `ExchangesBefore`, `ExchangesAfter`, `ListSessions`; every statement parameterised, nothing writes), and closes before returning. A token budget is the sum of `ceil(characters / 4)` per returned exchange; the cut marker, the error strings and the bounds are members of the service, pinned by tests. See `docs/transcripts.md#reading-the-archive`.

Table naming: `{tier}_{type}` (e.g., `hot_memories`, `cold_knowledge`, `pinned_memories`). Vec tables: `{table}_vec`. FTS tables: `{table}_fts`.
`MigrationRunner.TableName(tier, type)` is the canonical helper — use it, don't inline strings.

**Three table-pair arrays — know which includes pinned:**

- `TierNames.AllTablePairs` (`Memory/TierNames.cs`) and `EntryMapping.AllTablePairs` (`Server/Handlers/EntryMapping.cs`) — **8 pairs** (pinned included). Use these for runtime enumeration.
- `MigrationRunner.AllTablePairs` (`Storage/Schema.cs`) — **deliberately frozen at the 6 historical pairs**. Migrations 1–15 predate the pinned tier and must keep producing the same schema; Migration 16 creates the pinned tables with the full current column set instead of replaying the historical column evolution.

**Postgres:** no schema change for pinned — tier is a column on the `memories` / `knowledge` tables, so pinned is just a new `tier='pinned'` value (`PostgresMigrationRunner` is untouched).

## Embedding Layer

### IEmbedder

```csharp
interface IEmbedder
{
    Task<float[]> EmbedAsync(string text, CancellationToken ct = default);
    int Dimensions { get; }  // 384 for local bge-small-en-v1.5
}
```

**Factory**: `EmbedderFactory.CreateFromConfig(cfg.Embedding)` selects the implementation:
- `provider = "local"` (default) → `OnnxEmbedder` using bundled `models/bge-small-en-v1.5/model.onnx`
- `provider = "openai"` → `RemoteEmbedder` with OpenAI-compatible endpoint
- `provider = "bedrock"` → `RemoteEmbedder` with Amazon Bedrock

**Model path**: `ModelManager.cs` handles model discovery. It validates the bundled
`models/bge-small-en-v1.5/model.onnx` and throws a clear error if it is absent — it does **not**
download from HuggingFace. The model is fetched + sha256-verified at release build time
(`scripts/fetch-bge-small.sh`, pinned HF revision) and bundled into the per-RID release artifact;
for a git-source build, run `sh scripts/fetch-bge-small.sh` once to fetch it (it is not committed
to the repo / not in Git LFS).

`bge-small-en-v1.5` uses **CLS pooling** (not mean pooling) and an asymmetric query prefix:
search queries are embedded with the `bge` retrieval-instruction prefix while stored documents are
not. After swapping the local embedder the startup guard (`EmbedderMigration.EnsureCompatibleSqlite`,
called from `ServerComposition.OpenSqlite`/`OpenPostgres`/`OpenCortexCore`) detects a fingerprint
**mismatch** — or an **unstamped-but-populated** index (vectors present but no fingerprint, e.g. a
cortex DB created before stamping was wired into that path) — and **returns a decision** (it does no
re-embedding itself) per `embedding.on_model_change` (`OnModelChange`, default `auto`):
- `auto` → returns `ReindexInBackground`. Composition then starts an **in-process background worker**
  (its own SQLite connection + its own embedder) that re-embeds the sqlite / cortex **local** vec0
  index via `ReindexCoordinator` → `EmbeddingReindexer.RunBatched`. This is **never on the MCP boot
  path** — a synchronous re-embed of a large DB (~27 min for ~25k rows) would blow the stdio startup
  timeout into an atomic-rollback boot loop (the v3.0.2 regression this design fixes). `RunBatched`
  embeds OFF the write lock and commits per batch, advancing a `_meta` cursor (`embed.reindex.*`) so an
  interrupted run **resumes** instead of restarting; the coordinator takes a best-effort advisory lock
  (`embed.reindex.lock`) and stamps the fingerprint only after a full pass. While it runs, local
  retrieval is degraded; `session_start`/`status` surface `backgroundTasks.reindex` + a hint.
- `warn` → returns `Warned`: continues without re-stamping (recurring nag).
- `block` → throws `EmbedderFingerprintMismatchException`.
Postgres `auto` throws an explicit unsupported error (no local vec index to background-reindex). An
**empty** unstamped DB just stamps (genuinely fresh — nothing to migrate). For cortex only the local
index is migrated; the remote re-embeds independently via content-only sync. `total-recall
reindex-embeddings` runs the **same** `ReindexCoordinator` foreground (run-to-completion, also
resumable) — for `warn`/`block` deferrals and manual offline re-embeds.

**Known limitation — tokenizer accent handling**: the bundled F# WordPiece tokenizer lowercases but
does **not** strip accents (canonical BERT also strips accents). Accented words that don't match a
vocab entry therefore fall through to `[UNK]`. Impact is low for the English/code-heavy content this
memory system embeds; the behavior is pinned by a tokenizer test so it can't regress silently.

## Importers

### IImporter

```csharp
interface IImporter
{
    string SourceTool { get; }  // e.g., "claude-code"
    Task ImportAsync(CancellationToken ct);
}
```

Each importer:
1. Detects the host tool's memory directory (platform-specific paths)
2. Reads the host's memory format (markdown, JSON, etc.)
3. Deduplicates via `ImportLog` (content hash lookup in `import_log` table)
4. Calls `IStore.StoreAsync()` + `IVectorSearch.UpsertAsync()` for new entries

Importers run during `session_start` step 2. Order in `ServerComposition` matches the registration order.

**Memory import ids and crash repair.** An import that inserts a **memory** (today: Claude Code memory
files via `ImportUtils.ImportMarkdownFile` with `ContentType.Memory`, and the Hermes `MEMORY.md`/`USER.md`
sections) goes through `ImportUtils.InsertOrRepairMemory` (internal to the assembly). It derives the entry id from the import hash
(`ImportIds.FromHash`: first 16 bytes of `SHA-256(hash)`, lowercase `8-4-4-4-12`), so the same host memory is
the same entry on every machine (git sync relies on this), looks for an existing entry with that id in the
target tier and then the other tiers, and if one exists skips the insert and repairs it: it re-embeds the
**stored** text, inserts the vector (which replaces an orphan row) and writes the missing `import_log` row.
A kill between the insert, the embedding and the log row is therefore repaired by the next run instead of
leaving a duplicate. It is a repair on retry and not a transaction because in cortex mode importers write
through `RoutingStore`, which cannot share one. Knowledge imports keep random ids; memories imported before
this was added keep their random ids.

**Adding a new importer**: implement `IImporter`, add to the `importers` list in both `OpenSqlite`
and `OpenPostgres` / `OpenCortexCore` in `ServerComposition.cs`.

Current importers: `ClaudeCode`, `CopilotCli`, `Cursor`, `Cline`, `OpenCode`, `Hermes`, `ProjectDocs`.

## Ingestion

`FileIngester` → `HierarchicalIndex` → `TotalRecall.Core.Chunker` (F# pure) → `IStore` + `IVectorSearch`.

Flow:
1. `IngestValidator` checks for duplicate collections (by source path hash)
2. `Chunker.chunk()` splits file content into semantic chunks (Markdown heading-aware or regex code parser)
3. Each chunk is embedded and stored as a `cold_knowledge` entry with `collection_id` linking siblings
4. `HierarchicalIndex` tracks parent/child relationships via `parent_id`

**Supported parsers** (in `TotalRecall.Core/Parsers.fs`): Markdown, code (regex-based).

## Telemetry

| Class | Table | Purpose |
|-------|-------|---------|
| `CompactionLog` | `compaction_log` | Records tier movements (promote/demote/compact) with semantic drift and preservation ratio |
| `UsageEventLog` | `usage_events` | Raw token usage events (one row per assistant turn) |
| `UsageDailyRollup` | `usage_daily` | Aggregated daily token counts; 30-day raw retention |
| `UsageWatermarkStore` | `usage_watermarks` | Per-host scan watermark for incremental indexing |
| `RetrievalEventLog` | `retrieval_events` | Per-search retrieval events with score, tier, and outcome signal |

**Retrieval event logging**: `memory_search` and `kb_search` handlers call `LogRetrievalEvent()`
after each search. They pass `SessionConfigSnapshot.Resolve()` (pinned by `session_start`, resolved
lazily otherwise) so events are tagged to the session's config snapshot. Each event records a `query_source` (`assistant` / `web-ui` / `cli`)
so metrics can be scoped to assistant traffic; the search handlers return the logged event's
`retrievalId`, and `memory_feedback` calls `UpdateOutcome()` to mark whether it was used.

**Read-time outcome inference** (`Eval/Metrics.cs` → `Compute(events, threshold, nowMs, graceWindowMs, …)`):
outcomes are resolved when metrics are computed, not stored. `OutcomeUsed == true` is a hit;
`false` is a miss; `NULL` is a miss only once the event is older than `nowMs - graceWindowMs`
(otherwise it is pending and excluded). `eval_report`, the Insights health score, and the CLI
`eval report` all pass a grace window (default 60 min) so un-acted assistant retrievals age into
misses rather than silently counting as hits.

## Cortex Sync

`RoutingStore` wraps `SqliteStore`:
- Reads go to local SQLite (fast, offline-safe)
- Writes enqueue items to `sync_queue` AND write locally
- `SyncService` drains `sync_queue` → `CortexClient` HTTP calls
- `PeriodicSync` calls `SyncService` every N seconds (default 300s) on a background thread

**Offline resilience**: if Cortex is unreachable, local reads/writes continue. The queue
is durable (SQLite) and survives process restarts.

**Pinned is local-only (deliberate)**: the remote Cortex backend has no pinned-tier support
yet, so the pinned tier is excluded from every sync path:

- `RoutingStore` never enqueues pinned upserts or deletes to `sync_queue`
- `SyncService` pull/reconcile excludes pinned — remote updates and tombstones can never
  mutate a local pin
- `migrate_to_remote` silently skips pinned entries

Pinning an entry that already exists remotely leaves the remote copy alone (accepted edge:
a later re-pull can reintroduce it as a separate non-pinned entry). Lifting these gates
requires a companion Cortex server change — tracked in `docs/TODO.md`.

## Diagnostics

`ExceptionLogger.LogChain(prefix, ex)` walks the entire `InnerException` chain and writes to
`Console.Error` with indented `-> <Type>: <Message>` formatting. AOT-safe — no reflection.

**Use at every catch boundary** that can hit a static-constructor failure or P/Invoke failure:
- Migration guard
- Server composition (host startup)
- CLI commands that touch the embedder or open the DB

A bare `Console.Error.WriteLine(ex.Message)` at these boundaries hides `DllNotFoundException`
under `TypeInitializationException` and produces unactionable output.
