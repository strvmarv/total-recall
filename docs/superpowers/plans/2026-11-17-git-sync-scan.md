# Git sync 1b-i-1: the scan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the local scan that finds what the user changed in this machine's memories since the last pass, stamps each change with a hybrid logical clock stamp and records the stamps, hashes and clock in `git_sync_entry` and `_meta` in one write, with no network, no `git` and no change to any memory.

**Architecture:** The pure rules go in a new F# `SyncScan.fs` (the two hashes, the clock-warning kinds and `decide`, which maps one row and one local entry to one action). The I/O goes in C# `TotalRecall.Infrastructure/GitSync/`: `GitSyncRows` (typed access to `git_sync_entry`) and `GitSyncScanner` (one read snapshot over rows and memories, then one `BEGIN IMMEDIATE` write that applies the actions with stamps from `Clock.issue`). Nothing calls the scanner yet.

**Tech Stack:** F# (Expecto + FsCheck 2.16.6); C# net10 NativeAOT (xUnit 2.9.2, `Microsoft.Data.Sqlite`). No new package.

**Spec:** `docs/superpowers/specs/2026-11-17-git-sync-scan-design.md` (read it first; this plan gives files, signatures and test lists, the spec gives the rules and the numbered decisions, cited as "decision N"). The umbrella is `2026-11-15-git-sync-design.md`.

- Core has no I/O and no mutable state and uses no `%A` or reflection serialization. C# is AOT-safe: no reflection serializer, no `Regex` without a source generator, no `dynamic`.

## Interpretations (recorded here because the spec is read-only)

1. **The hash encoding** (decision 5). Content hash = SHA-256, lowercase hex, of `"total-recall/scan/content/v1\n"` (UTF-8) followed by six fields in this order: text, project, scope, entry type name (`SyncRecord.entryTypeName`), source tool name (`SyncRecord.sourceToolName`), `created_at` as decimal ASCII. A field is `0x00` when absent, else `0x01`, a 4-byte big-endian byte length and the UTF-8 bytes (project and scope are `None` when empty, so `Some ""` cannot occur; the encoding still distinguishes it). Tags hash = SHA-256 of `"total-recall/scan/tags/v1\n"`, a 4-byte big-endian count of `normaliseTags tags`, then each tag as a 4-byte big-endian length and its UTF-8 bytes. Golden vectors (computed independently with Python `hashlib`): the content hash of text `Use bun, not npm.`, no project, no scope, `correction`, no source, `1700000000000` is `b00db27deb3dd59a9ce9fbc157ae4fa7b7ee29799768e96ef205fa4da3f3d555`; with project and scope `owner/repo`, `preference`, `claude-code` it is `8784f24f7c15de98e269095d90e4aac6cfe913b936a8171806739ebfb9da1074`; text empty, `imported`, created `0`, no others: `31359dca578b1c21fc1a393c63c229a88e010f17c363b1668e0177dd66946fc3`; the same with project `Some ""`: `ac9d1ec71fa87889d01c78a210a142ebe0b1211244839d5de10520aa5e6d42e7`. Tags: `[]` is `fa1fe07c4559a10134239fa0a1ddfd44cb9ebe62e082284aa674591f50b06625`; `["a";"b"]`, `["b";"a";"a"]` are both `53889f8670d446d8752914136774e43e12f3811fe286f7800c82e1b38ef9e689`.
2. **Core names.** `SyncScan.contentHash : ContentFields -> string`, `SyncScan.tagsHash : string list -> string`, `SyncScan.decide : RowView option -> LocalEntry option -> bool -> ScanAction` (third argument: the id exists as a knowledge entry), `SyncScan.floorStamp : Stamp option -> Stamp option -> Stamp option` (the greater of two, decision 11) and a module `SyncScan.ClockWarning` (`Kind`, `kindName`, `addKinds : string option -> Kind list -> string option`, returning the new stored text, or `None` when nothing changed: the stored value if it already holds every kind, so the caller writes only on `Some`). The `RowView`, `BaseFacts`, `GroupAction`, `RowChanges` and `ScanAction` types are in Task 1.
3. **Rows.** `GitSyncRow` is a C# record over the 15 columns of `git_sync_entry` with `State` as `SyncMerge.RowState` and the three tiers/stamps as typed values; stamps are stored as `Stamp.format` text; `GitSyncRows` is a static class on a connection and an optional explicit transaction (the scan uses raw `BEGIN`/`COMMIT`, so it passes none): `ReadAll(conn) : Dictionary<string, GitSyncRow>` and `Write(conn, row)` (`INSERT ... ON CONFLICT(entry_id) DO UPDATE`; read, insert and update only, as the spec's interface lists: no delete in this milestone). From C#, the F# modules that share a name with a type are reached by their compiled names, as `RecordWriter.cs` does: `SyncStamp.StampModule.format`/`tryParse`, `SyncStamp.ClockModule.issue`/`guardStartup`/`serialize`/`tryDeserialize`, `SyncStamp.MachineIdModule.tryCreate`/`value`, and `using SyncRecordModule = TotalRecall.Core.SyncRecord;` for `tierName`, `tryParseTier`, `tierRank`, `entryTypeName`, `sourceToolName`, `normaliseTags`; `Tier` is an F# union (a reference type: compare with `.IsHot` / `Equals`, never `==` on a possibly null value). An unknown stored state, tier or stamp text is read as the column's "nothing seen" value (state `Active` is not guessed: an unknown state makes `ReadAll` throw `FormatException`, which the scanner reports as `Failed`; the table's CHECK keeps it from happening).
4. **Transactions.** Microsoft.Data.Sqlite's `BeginTransaction()` is deferred, so the scanner runs `BEGIN` / `COMMIT` for the snapshot and `BEGIN IMMEDIATE` / `COMMIT` (`ROLLBACK` in a `finally` on failure) for the write as plain commands with no `SqliteTransaction` object; WAL gives the read transaction its snapshot at the first `SELECT`. **Hygiene:** the snapshot always ends (`COMMIT`, or `ROLLBACK` when it threw) in a `finally`, so a failed read never leaves the connection inside a transaction; the write `ROLLBACK` runs only when `BEGIN IMMEDIATE` succeeded and any exception from a rollback is swallowed, so a lock timeout on `BEGIN IMMEDIATE` returns `Failed(reason)` and not a rollback error. `EmbeddingReindexer.cs` already uses the same raw `BEGIN IMMEDIATE`/`COMMIT` pattern.
5. **Scanner API.** `new GitSyncScanner(MsSqliteConnection connection, Func<long> nowMs)`; `ScanOutcome Scan()`. `ScanOutcome` is an abstract record with `Done(ScanSummary Summary)`, `NotJoined` and `Failed(string Reason)`. `ScanSummary(int New, int Content, int Tags, int Sticky, int Tier, int Left, int Reactivated, int Ineligible, IReadOnlyList<LocalDeletion> LocalDeletions, IReadOnlyList<SkippedItem> Skipped)`; `LocalDeletion(string Id, bool HasBase, bool HasPushingStamps)`; `SkippedItem(string Id, string? Group, string Reason)` where `Group` is `content`, `tags`, `sticky`, `tier` or null. The counts are numbers of entries: `New` counts `NewRow`, `Reactivated` counts `Reactivate`, `Left` counts `MoveToLeft`; for `UpdateRow`, `Content`, `Sticky` and `Tier` count an `IssueStamp` of that group (an entry that stamped two groups counts in both; `StoreValue` and `DropPendingStamp` count nowhere) and `Tags` counts a `StoreValue` of the tags group; `NewRow` and `Reactivate` count only in `New`/`Reactivated`; `Ineligible` is the number of ineligible-id entries seen.
6. **Seams** (decision 13), both `internal` on the scanner (the test project has `InternalsVisibleTo`): `Action? AfterFirstTableRead` (called once, after the hot memory table was read and before the warm one) and `Action<string>? BeforeWrite` (called inside the open write transaction with a step name before each of the four steps `rows`, `issues`, `clock`, `warning`, whether or not the step has anything to write, so a fault test is deterministic; a test makes sure a write transaction opens by changing something first); `int WriteTransactionCount` (incremented when a write transaction is opened).
7. **Reading entries.** `SELECT *` from `hot_memories`, `warm_memories`, `cold_memories` in that order, then `SELECT id FROM <tier>_knowledge` for the three knowledge tables, all through commands created on the scanner's connection (no `Transaction` property is needed under a raw `BEGIN`), mapped with `SqliteStore.RowToEntry` (internal, same assembly). `sticky` is read from the hot table's `sticky` column; warm and cold are never sticky. Any non-fatal exception from `RowToEntry` (`catch (Exception ex) when (ex is not OutOfMemoryException)`: `FormatException` from tags, `ArgumentException` from the source tool, `InvalidCastException` from a NULL `access_count` or `decay_score`, which the schema allows) skips that entry (decision 3).
8. **Ineligible issues** (decision 2): `git_sync_issue(entry_id, kind='ineligible-id', record_hash=NULL, attempts=0, detail=<tier name>)`; the id and tier are read from the row's `id` column before `RowToEntry` runs, so an unreadable entry with an ineligible id still gets its issue. An ineligible id found in two tiers yields **one** candidate (the first of hot, warm, cold), so `(entry_id, kind)` stays unique and the `detail` does not flip between scans.
9. **The base facts** (decision 11): the scanner parses `base_json` with `RecordReader.Parse(utf8, SyncValidation.recordPath id)`; a valid parse gives `BaseFacts { Tier = Some record.Placement.Tier; ContentStamp; StickyStamp = Some placement.StickyStamp; TierStamp = Some placement.TierStamp }`; a parse that is rejected, an id that is not eligible or invalid UTF-8 gives `Some { Tier = None; all stamps None }` ("has a base, tier unknown, no floor"); a NULL `base_json` gives `None`. `HasPushingStamps` is false when `pushing_stamps` is NULL, empty, whitespace, `{}` or `[]`, true otherwise (the encoding is left open by the store-schema design; 1b-i-3 may fix it and then this one function changes).
10. **Clock warning text** (decision 11): `clock: ` followed by the stored kind names (`clock-reset`, `clock-unreadable`, `far-future`, `exhausted`) sorted ordinally and joined by `,`.

## Review Focus

1. A second scan with nothing to do writes nothing even while a skipped group, a far-future floor or an ineligible id is still there [Task 5: `SecondScan_WithRecurringConditions_WritesNothing`].
2. A pin made on a warm entry (so it is hot and sticky, and promoted) is stamped once per group and never as a colder tier; a promotion undone before a push leaves no tier stamp [Task 4: `Pin_OnAWarmEntry_StampsStickyAndTier`, `UndonePromotion_DropsThePendingTierStamp`].
3. An entry moved between tiers by another connection while the scan reads is seen once and never as a deletion [Task 5: `AMoveIntoAnAlreadyReadTier_IsSeenOnce_AndNeverADeletion`, `AMoveOutOfAnAlreadyReadTier_IsNotSeenTwice`].
4. A memory with an unreadable `source_tool` or invalid tags, and an id present in two tiers, never stop the scan and are never reported as deleted [Task 3: `UnreadableEntries_AreSkippedAndListed`, `AnIdInTwoTiers_IsSkipped`; Task 4: `AnUnreadableOrDuplicatedEntryWithAnActiveRow_IsNotADeletion_RowUntouched_OthersStamped`].
5. A write failure at any step leaves rows, issues, clock and warning as before [Task 5: `AFaultInEachWriteStep_LeavesEverythingAsBefore`].
