# Git sync 1b-i-3: the push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the push of the sync cycle: after a complete pull, write this machine's changed memories into the local clone as patches of the records already there (a new memory becomes a new record), commit once, push without force, then make the rows and `L` say what was pushed. Nothing calls the new classes yet.

**Architecture:** Pure rules in a new F# `SyncPush.fs` (which entries and groups are sent, the exclusions, the new record, the row after a push, the commit message, the machine label, the `published` mapping, the staged-set check). Two new closed git commands (`StagePaths`, `StagedSet`). C# `GitSyncPusher` (partial classes: prepare, plan transaction, write/commit/push, finalize) in `TotalRecall.Infrastructure/GitSync`.

**Tech Stack:** F# (Expecto + FsCheck); C# net10 NativeAOT (xUnit, `Microsoft.Data.Sqlite`). No new package.

**Spec:** `docs/superpowers/specs/2026-11-17-git-sync-push-design.md` (read it first; this plan gives files, signatures and test lists, the spec gives the rules, cited as "decision N" and "AC N"). Also the pull design `2026-11-17-git-sync-pull-design.md` and the umbrella `2026-11-15-git-sync-design.md`.

## Global Constraints

- The spec file is read-only for the whole run. Commits carry no trailer and no AI attribution; messages are plain imperative sentences.
- Core has no I/O, no mutable state, no `%A`. C# is AOT-safe: no reflection serializer, no `Regex` without a source generator, no `dynamic`. Nothing outside the new pusher and its tests calls `GitSyncPusher` (a test greps for it).
- `SyncPush.fs` goes into `TotalRecall.Core.fsproj` directly after `SyncApply.fs`, its tests into `TotalRecall.Core.Tests.fsproj` after `SyncApplyTests.fs`.
- The push writes: `git_sync_entry` rows, `_meta.git_sync_last_sha`, the clone (files under `memories/`, temporary files under `.git`, `.git/info/attributes`, one commit, the protective ref) and the remote branch. It writes no memory, vector, `import_log` or `git_sync_issue` row, takes no lock, runs no scan, no fetch, and no network command but the push.
- The push never removes a file and never force-pushes: the commit message always ends `-0`; the push command is the client's existing `Push` (no `+`, no force option).
- Limits and text are the spec's: record at most 262144 bytes (`SyncValidation.maxRecordBytes`), at most 64 distinct tags, a tag at most 128 UTF-16 units, stage batches of at most 100 paths, label at most 40 characters of `A-Z a-z 0-9 . _ -`, else `unknown`.
- Test commands: `dotnet test tests/TotalRecall.Core.Tests/TotalRecall.Core.Tests.fsproj`; `dotnet test tests/TotalRecall.Infrastructure.Tests/TotalRecall.Infrastructure.Tests.csproj --filter "FullyQualifiedName~<Class>"` (the `NU1903` warning is expected). Baseline flaky test: `SummarySanitizerTests.Sanitize_Hostile4000CharInput_FinishesUnder100Ms`.
- Tests use temporary files and real git (`PullRig`/`BareRemote`/`GitTestEnvironment`, `[GitFact]`), never the real `~/.total-recall`. Windows is the owner's platform: `Path.Combine`, dispose connections before deleting (`ClearAllPools`), no read-only-pack assumptions. This worktree has `node_modules` and `models/bge-small-en-v1.5` symlinked to the main checkout.

## Interpretations (recorded here because the spec is read-only)

1. **Candidates without reading every entry** (decision 4): a row is a candidate when it is `active` and has no base, or a pending content/sticky/tier stamp, or `scanned_tags_hash` (not NULL) differs from `SyncScan.tagsHash` of the base's tags (the base is parsed with `RecordReader.Parse`; a NULL hash is "nothing seen" and is not a difference: the next scan stores it). The entry is read (`LocalEntryReader.Read` through the store, then again inside the plan transaction) only for a candidate. A row whose base text cannot be parsed and that has no pending stamp is not a candidate (nothing says it changed); one that has a pending stamp is `unreadable-base`.
2. **Core names** (`module TotalRecall.Core.SyncPush`): `Exclusion` (`Issue | RejectedRecord | NotReconciled | RecordMissing | RecordUnreadable | UnreadableBase | PathOccupied | BlockedElsewhere | UnreadableEntry`) with `exclusionName` giving `issue`, `rejected-record`, `not-reconciled`, `record-missing`, `record-unreadable`, `unreadable-base`, `path-occupied`, `blocked-elsewhere`, `unreadable-entry`; the other reason words are `changed-since-scan`, `stale-stamp`, `missing-stamp` and the block names `too-large`, `too-many-tags`, `tag-too-long`, `ineligible-id`, `not-encodable`.
3. **Label** "reduced to the allowed characters" means every other character is **removed** (not replaced); an empty result or a name that becomes empty is `unknown`; cut at 40 after removing.
4. **`base_json` after a push** is the canonical text: for a written entry the bytes written (UTF-8); for an unchanged entry `RecordWriter.Write(parsed record at L)` (so a non-canonical blob is stored normalised); both decoded with strict UTF-8.
5. **Failure kind words** of `PushOutcome.Failed`: the git client's `FailureKind` text for a failed git call (`Network`, `Auth`, `Cancelled`, ...), and `Busy`, `Store`, `Clone` (reset, clean, `rev-parse`, the info file), `Write`, `Stage`, `StagedSet`, `Commit`, `Finalize`, `Meta`, `Ref`, `Cancelled` for local steps. `NonFastForward` is never a `Failed` kind.
6. **Seams** on `GitSyncPusher` (all `internal`): `Action? BeforePlanTransaction`, `Action<string,string>? BeforeStep` (an id, or `""` for a step that is not per entry, and the step name: in the plan transaction `reread`, `plan`, `pushing`, `block`; between steps `write` (id, before the rename), `stage` (`""`, before each `StagePaths` batch), `commit` (`""`, before the commit); in the finalize transaction `finalize` (id), `meta` (`""`); after it `ref` (`""`)), `Action? BeforePush` (immediately before the push command: a test makes the remote move here), `int TransactionCount`. A hook that throws is the fault: it becomes the step's `Failed`. A hook is called inside the transaction when the step is one.
7. **Pending-stamp equality** in the finalize is `SyncStamp.Stamp` structural equality.
8. **`Skipped`** of `PushSummary` also lists an entry written with a stale group, with reason `stale-stamp` (the entry is in `Written` too).

## Review Focus

1. A machine name with spaces, non-ASCII, empty or longer than 40 characters never reaches a path or breaks a commit message [Task 2: `machineLabel` cases].
2. Text with `$Id: x$`, CRLF, a lone surrogate or a NUL is committed byte for byte or blocked as `not-encodable`, whatever attributes the repository tracks [Task 6: `ATrackedIdentAttribute_DoesNotChangeTheCommittedBytes`, Task 4: `ALoneSurrogate_BlocksAsNotEncodable`].
3. A first push of hundreds of new memories (Windows command-line limit) [Task 6: `TwoHundredFiftyNewEntries_AreStagedInThreeBatches`].
4. A hostile or odd repository: case-variant paths, a `.gitignore` covering `memories/`, a blob where a directory goes, a commit and an untracked file left by an earlier failed push [Task 4 and Task 6].
5. A crash or lost answer at any point: the next pull recovers and nothing is sent twice [Task 7: the lost-response and failed-finalize tests].
