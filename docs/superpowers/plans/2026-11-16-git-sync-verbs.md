# Git sync 1a-3: the `sync init`, `join`, `leave` and `status` commands Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the four hidden `sync` commands that set a machine up against a git sync repository (`init`, `join`), switch it back (`leave`) and describe it (`status`), with the pure rules in `TotalRecall.Core`, the service in `TotalRecall.Infrastructure/GitSync/`, and thin commands in `TotalRecall.Cli`.

**Architecture:** Pure rules (address credentials, storage-mode verdict, same-repository and machine-id rules, ids, status text, `ls-remote` ref parsing) go in a new F# `SyncSetup.fs` plus two small edits to `SyncGit.fs` and `Config.fs`. A `SyncSetupService` (C#, all collaborators injected) runs the preconditions, `init`, `join`, `leave` and `status` against `GitClient`, `RepoGuard`, `SyncLock`, a SQLite connection and a user-config seam, and reports through a callback. Four thin `ICliCommand`s in a hidden `sync` group parse arguments, build the production environment and print.

**Tech Stack:** F# (Expecto + FsCheck 2.16.6) for the pure part; C# net10 NativeAOT (xUnit 2.9.2, `Microsoft.Data.Sqlite`, `Process` through the existing `GitProcess`). No new package.

**Spec:** `docs/superpowers/specs/2026-11-16-git-sync-verbs-design.md` (read it first; this plan gives files, signatures and test lists, the spec gives the rules and the numbered decisions, cited as "decision N").

## Global Constraints

- The spec file is read-only for the whole run. Commits carry no trailer and no AI attribution; messages are plain imperative sentences.
- Core has no I/O and no mutable state and uses no `%A` or reflection serialization. C# is AOT-safe: no reflection serializer, no `Regex` without a source generator (use `string` and `Span` code), no `dynamic`.

- No message, result, exception text or output line holds an address except through `SyncSetup.displayRemote`; git's own standard error is already redacted by the client.
- No test reads or writes the developer's real `~/.total-recall`, `~/.gitconfig` or the network. Tests that go through the CLI set `TOTAL_RECALL_HOME` and `TOTAL_RECALL_DB_PATH` to a temporary directory inside the existing `process-environment` collections; git tests use the 1a-1/1a-2 support code (`GitTestEnvironment`, `BareRemote`, `RecordingGitProcess`, `ForceFlags`, `GuardSettings`, `StubProbe`, `[GitFact]`).

## Interpretations (recorded here because the spec is read-only)

1. **The service is one class, the commands are thin.** `SyncSetupService` (Infrastructure) holds the four operations; its input is one record `SyncSetupEnvironment`; its output is `SetupResult` (exit code, optional refusal name and text, result lines, `note:` lines). Notices and git progress go through `SyncSetupEnvironment.Report` while they happen. The commands print the result.
2. **Names.** Refusal names are the `Refusal` DU of `SyncSetup.fs` with `refusalName`; the spec's `SyncSetup.userInfoOf` is `addressUserInfo` (a different reader from `SyncGit.userInfoOf`, as decision 4.1 says). `RemoteShape` is `Empty | BranchPresent | OtherRefs` and the spec's `classifyRemote` is named `classifyRefs` (it takes the ref names and the branch), because `SyncGit.classifyRemote` already exists with another meaning.
3. **`ICliCommand.Hidden`** is a default interface member (`bool Hidden => false;`); existing implementers and the test registry stub compile unchanged.
4. **Production wiring** lives in `Commands/Sync/SyncSetupFactory.cs` (loads the config, resolves the paths, finds nothing at construction time): it is the only place that reads the process environment for these commands.
5. **The store.** `init`/`join` open `SqliteConnection.Open(path, pooling: false)` + `MigrationRunner.RunMigrations` and use the raw connection (and `new SqliteStore(connection)` for `IMetaStore`); the service disposes the connection.
6. **Failure kinds.** `GitResult.Failure` is `SyncGit.FailureKind?`; the mapping to refusal names is one private function `Classify(GitResult, Step)` in the service (decision 5.1 and 6.1/6.2 differ only for `OutputTooLarge`, and the push adds the "may have completed" text after `TimedOut`/`Network`).
7. **`displayRemote` is stricter than decision 14 where decision 14 would print a secret.** A user-info holding `:` on **any** scheme, and any user-info on `http`, `https`, `git`, `file`, `ftp`, `ftps`, is shown entirely as `***` (`https://***@h/x`, `ssh://***@h/x`), not `<text before the colon>:***`: a token can be the user name (`https://ghp_x:x-oauth-basic@github.com/...`). A plain ssh login (`git@h`) is shown as written. The tests assert the stricter output; the spec's intent (no command prints a credential) is unchanged.
8. **Test seams the spec leaves to the plan.** `SyncSetupEnvironment` carries `Move` (`Action<string,string>?`, default `Directory.Move`, used by `CloneSideline` and by the decision-10.1(b) old-clone move) and `LoadError` (`string?`: set by the factory when the config or the database path could not be resolved; `init`/`join`/`leave` answer `failed` with it, `status` prints `unknown (<reason>)` for the facts that need them and exits 0). `CloneSideline.Move` takes the same optional `Action<string,string>`.
9. **Ownership and lifetimes.** `Prepared` is created by the private `PrepareAsync` and **owns** the lock handle and the SQLite connection; the public methods `InitAsync`/`JoinAsync`/`LeaveAsync` dispose it in `finally`. `Prepared` carries: `Address`, `Branch`, `Paths` (`For`), `Client`, `Guard` (in-memory settings for the address), `Connection`, `Meta` (`IMetaStore` over a borrowed `SqliteStore`), `Stored` (`SyncIdentity.StoredIdentity`), `PreviousBranch` (`string option`), `Fingerprint`, `Lock`. `RecordAsync(Prepared p, RecordPlan plan)` where `record RecordPlan(RecordKind Kind, string RepoId, bool ReusedClone, bool SameRepository, string? OldCloneDirectory)` and `enum RecordKind { Init, JoinDifferent, JoinSame }`; `LeaveAsync` uses the private `WriteConfig(keys)` that `RecordAsync` also uses (decision 10.3).
10. **The registry for tests.** `CliApp` gains `public static IReadOnlyList<ICliCommand> GetRegistryForTestsInternal()` (the production registry), next to the existing `SetRegistryForTestsInternal`, so Cli tests can enumerate every command's help and build a registry without the sync commands.
11. **Test support.** Task 5 adds to `tests/TotalRecall.Infrastructure.Tests/GitSync/`: `SyncSetupTestSupport.cs` with `SetupRig` (temp data directory, database path, fake `IUserConfigFile`, `StubProbe`, a clock, fixed random bytes, a `HostIdentity` over a fixed id, the `Report` list, the `Move` seam), `FaultingGitProcess(IGitProcess inner, Func<SyncGit.GitCommand, GitResult?> fault, Action<SyncGit.GitCommand>? before = null)` (answers a canned failure for a command, and runs a hook before the real command: used for the race and the rename/fetch failures), and public helpers on `BareRemote`/a new `CleanBare` (`Git(...)`, `AddRef(name, sha)`, `InstallHook(name, script)`) so refs, tags and a `pre-receive` hook can be added **in a clean environment**: every bare repository in these tests is made with a clean home (the hostile global config sets `init.defaultObjectFormat=sha256`, `defaultRefFormat=reftable` and a global `core.hooksPath`, which would make the bare repository unusable by the sha1 client and silence its hooks). The hostile config reaches **only the client** (`GitClientOptions.EnvironmentOverrides`), and the rejected-push test uses the clean config with `[GitShFact]`.
12. **The Cli end-to-end tests isolate git too.** They set `HOME`, `GIT_CONFIG_GLOBAL` (an empty temp file) and `GIT_CONFIG_NOSYSTEM=1` next to `TOTAL_RECALL_HOME`/`TOTAL_RECALL_DB_PATH` inside the `ConsoleCapture` collection, create the bare repository with `git init --bare -b main` in that environment, and skip when `git` is absent (a small `GitAvailableFact` in Cli.Tests).

## Review Focus

1. A repository recreated at the same address (a different `repo_id` there) never keeps the old clone's `refs/total-recall/last-synced`; a transient fetch failure never sidelines a healthy clone [Task 8: `Join_ARepositoryRecreatedAtTheSameAddress_DropsTheOldProtectiveRef`, `Join_ATransientFetchFailure_KeepsTheClone`].
2. `status` on a cleanly closed WAL database in a directory named `a#b?c%41;d e` reads the right identity and creates no file; with exactly one of the two sidecars it opens nothing [Task 4: `ReadOnlyDatabaseTests`; Task 6: `Status_OnACleanDatabase_CreatesNothing`].
3. An address holding a credential in any accepted form (`https://tok@h/x`, `ssh://git:pw@h/x`, `file://tok:pw@h/x`, `https://user:pa?ss@h/x`, `https://h/x?token=y`) is refused by `init`/`join` and printed nowhere, and a legitimate address (`https://h/o/repo@v2.git`, `host:team/repo@2.git`, `https://[::1]:8080/o/r`) is accepted [Task 2: `AddressTable`; Task 5: `Preconditions_RefuseEachCredentialAddress`].
4. A push that fails, a refused precondition and a refused manifest leave the database, the config and the remote as they were, and the retry works; a crash between the record steps is repaired by running the command again [Task 7: `Init_APushRejectedByTheRemote_RecordsNothing`, `Init_FaultsBetweenTheRecordSteps_AreRepaired`; Task 8: `Join_FaultsBetweenTheRecordSteps_AreRepaired`].
5. An old-format database is never stamped by the schema runner, and `init`/`join` never run the orphan sweep that deletes content rows [Task 4: `LegacyDatabaseProbeTests`; Tasks 7 and 8: `..._LeavesAnOrphanContentRowInPlace`].
6. The commands are invisible to anyone who never types `sync`: top-level help (apart from the version line), every other help, the catalog and the user-facing documents do not mention them [Task 9: `TopLevelHelp_IsTheSameWithoutTheSyncCommands`, `NoUserFacingDocumentNamesTheSyncCommands`].
