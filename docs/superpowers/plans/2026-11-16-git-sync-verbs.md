# Git sync 1a-3: the `sync init`, `join`, `leave` and `status` commands Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the four hidden `sync` commands that set a machine up against a git sync repository (`init`, `join`), switch it back (`leave`) and describe it (`status`), with the pure rules in `TotalRecall.Core`, the service in `TotalRecall.Infrastructure/GitSync/`, and thin commands in `TotalRecall.Cli`.

**Architecture:** Pure rules (address credentials, storage-mode verdict, same-repository and machine-id rules, ids, status text, `ls-remote` ref parsing) go in a new F# `SyncSetup.fs` plus two small edits to `SyncGit.fs` and `Config.fs`. A `SyncSetupService` (C#, all collaborators injected) runs the preconditions, `init`, `join`, `leave` and `status` against `GitClient`, `RepoGuard`, `SyncLock`, a SQLite connection and a user-config seam, and reports through a callback. Four thin `ICliCommand`s in a hidden `sync` group parse arguments, build the production environment and print.

**Tech Stack:** F# (Expecto + FsCheck 2.16.6) for the pure part; C# net10 NativeAOT (xUnit 2.9.2, `Microsoft.Data.Sqlite`, `Process` through the existing `GitProcess`). No new package.

**Spec:** `docs/superpowers/specs/2026-11-16-git-sync-verbs-design.md` (read it first; this plan gives files, signatures and test lists, the spec gives the rules and the numbered decisions, cited as "decision N").

## Global Constraints

- The spec file is read-only for the whole run. Commits carry no trailer and no AI attribution; messages are plain imperative sentences.
- Core has no I/O and no mutable state and uses no `%A` or reflection serialization. C# is AOT-safe: no reflection serializer, no `Regex` without a source generator (use `string` and `Span` code), no `dynamic`.
- New F# files are added to `TotalRecall.Core.fsproj` directly after `SyncSettingsGuard.fs`, and their test files after `SyncSettingsGuardTests.fs` in `TotalRecall.Core.Tests.fsproj`.
- No message, result, exception text or output line holds an address except through `SyncSetup.displayRemote`; git's own standard error is already redacted by the client.
- No test reads or writes the developer's real `~/.total-recall`, `~/.gitconfig` or the network. Tests that go through the CLI set `TOTAL_RECALL_HOME` and `TOTAL_RECALL_DB_PATH` to a temporary directory inside the existing `process-environment` collections; git tests use the 1a-1/1a-2 support code (`GitTestEnvironment`, `BareRemote`, `RecordingGitProcess`, `ForceFlags`, `GuardSettings`, `StubProbe`, `[GitFact]`).
- Test commands: `dotnet test tests/TotalRecall.Core.Tests/TotalRecall.Core.Tests.fsproj`; `dotnet test tests/TotalRecall.Infrastructure.Tests/TotalRecall.Infrastructure.Tests.csproj --filter "FullyQualifiedName~<Class>"`; `dotnet test tests/TotalRecall.Cli.Tests/TotalRecall.Cli.Tests.csproj`. ## Interpretations (recorded here because the spec is read-only)

1. **The service is one class, the commands are thin.** `SyncSetupService` (Infrastructure) holds the four operations; its input is one record `SyncSetupEnvironment`; its output is `SetupResult` (exit code, optional refusal name and text, result lines, `note:` lines). Notices and git progress go through `SyncSetupEnvironment.Report` while they happen. The commands print the result.
2. **Names.** Refusal names are the `Refusal` DU of `SyncSetup.fs` with `refusalName`; the spec's `SyncSetup.userInfoOf` is `addressUserInfo` (a different reader from `SyncGit.userInfoOf`, as decision 4.1 says). `RemoteShape` is `Empty | BranchPresent | OtherRefs` and `classifyRemote` takes the ref names and the branch.
3. **`ICliCommand.Hidden`** is a default interface member (`bool Hidden => false;`); existing implementers and the test registry stub compile unchanged.
4. **Production wiring** lives in `Commands/Sync/SyncSetupFactory.cs` (loads the config, resolves the paths, finds nothing at construction time): it is the only place that reads the process environment for these commands.
5. **The store.** `init`/`join` open `SqliteConnection.Open(path, pooling: false)` + `MigrationRunner.RunMigrations` and use the raw connection (and `new SqliteStore(connection)` for `IMetaStore`); the service disposes the connection.
6. **Failure kinds.** `GitResult.Failure` is `SyncGit.FailureKind?`; the mapping to refusal names is one private function `Classify(GitResult, bool afterPush)` in the service.

## Review Focus

1. A repository recreated at the same address (a different `repo_id` there) never keeps the old clone's `refs/total-recall/last-synced`; a transient fetch failure never sidelines a healthy clone [Task 8].
2. `status` on a cleanly closed WAL database in a directory named `a#b?c%41;d e` reads the right identity and creates no file; with one of the two sidecars it opens nothing [Tasks 5, 6].
3. An address holding a credential in any accepted form (`https://tok@h/x`, `ssh://git:pw@h/x`, `file://tok:pw@h/x`, `https://user:pa?ss@h/x`, `https://h/x?token=y`) is refused by `init`/`join`, is stored nowhere and printed nowhere, and a legitimate address (`https://h/o/repo@v2.git`, `host:team/repo@2.git`, `https://[::1]:8080/o/r`) is accepted [Tasks 2, 7].
4. A push that fails, a refused precondition and a refused manifest leave the database, the config and the remote as they were, and the retry works; a crash between the record steps is repaired by running the command again [Tasks 6, 7, 8].
5. The commands are invisible to anyone who never types `sync`: top-level help, the catalog and every other message are byte-identical [Task 9].
