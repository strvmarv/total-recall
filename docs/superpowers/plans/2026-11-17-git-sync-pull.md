# Git sync 1b-i-2: the pull Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the pull of the sync cycle: fetch the remote branch into the local clone (with the repository guard and the proof state) and apply what the repository holds to this machine's memories, one entry in one transaction at a time, with the existing pure merge decisions. Everything that needs a part not built yet (deletions, review items, re-push marks) is postponed and reported. Nothing calls the new classes yet.

**Architecture:** Pure rules in a new F# `SyncApply.fs` (postponement, the `pushing_stamps` codec, the hot limit, the visit set, the next row). C# in `TotalRecall.Infrastructure`: store groundwork (immediate store transaction that also carries the sync-table statements, source tool and `created_at` updates, vector replacement, row delete, issue access, one shared local-entry reader), `BaseRenderer`, `GitSyncFetcher`, and `GitSyncApplier` (tree reading, one entry per transaction, issues, the advance of `L`).

**Tech Stack:** F# (Expecto + FsCheck 2.16.6); C# net10 NativeAOT (xUnit 2.9.2, `Microsoft.Data.Sqlite` 10.0.5). No new package.

**Spec:** `docs/superpowers/specs/2026-11-17-git-sync-pull-design.md` (read it first; this plan gives files, signatures and test lists, the spec gives the rules, cited as "decision N"). Also the scan's `2026-11-17-git-sync-scan-design.md` and the umbrella `2026-11-15-git-sync-design.md`.

## Global Constraints

- The spec file is read-only for the whole run. Commits carry no trailer and no AI attribution; messages are plain imperative sentences.
- Core has no I/O and no mutable state and uses no `%A`. C# is AOT-safe: no reflection serializer, no `Regex` without a source generator, no `dynamic`. No file outside the new code calls `GitSyncFetcher` or `GitSyncApplier`.
- New F# files go into `TotalRecall.Core.fsproj` directly after `SyncScan.fs` (and the test file after `SyncScanTests.fs`).
- The pull writes the memory tables, vectors and `import_log` only inside an entry's transaction; it writes `git_sync_entry`, `git_sync_issue` and `_meta` `git_sync_last_sha`/`git_sync_hlc`, and the clone and its protective ref. It never writes `git_sync_last_ok`/`git_sync_last_error` or `git_sync_arrivals`, takes no lock and runs no scan.
- Test commands: `dotnet test tests/TotalRecall.Core.Tests/TotalRecall.Core.Tests.fsproj`; `dotnet test tests/TotalRecall.Infrastructure.Tests/TotalRecall.Infrastructure.Tests.csproj --filter "FullyQualifiedName~<Class>"`. The whole verify is the profile's list (`node skills/develop/scripts/profile.js verify-files .github/develop.md <dir>`) plus `node scripts/host-docs.test.js`; it includes the catalog guard (`dotnet run --project src/TotalRecall.Host -c Release -- dump-catalog | diff catalog.json -`, only a trailing newline and `NU1903`) and the AOT publish (no warning but `NU1903`).
- A test name quotes the spec's rule or the ticket's wording. Tests use temporary files (`SyncDb.OpenMigrated`, `ScanRig`-style rigs, `BareRemote` and `GitTestEnvironment` for real git, `[GitFact]`), never the real `~/.total-recall`. Windows is the owner's platform: `Path.Combine`, dispose connections before deleting (`ClearAllPools`), no read-only-pack assumptions. A worktree needs the `node_modules` symlink and `models/` (see the scan plan, Interpretation 11g) to run the Infrastructure tests.

## Interpretations (recorded here because the spec is read-only)

1. **Core names** (`module TotalRecall.Core.SyncApply`): `PostponeReason = Deletion | Review | Repush`, `reasonName`, `postponement : MergeDecision -> PostponeReason option` (decision 8: `Deletion` when the entry outcome is `DeleteEntry`/`HoldDeletion _`/`PushDeletion`, or there is a note, `FreshContentStamp`, `CloseHeldDelete`, or `RowState = Some Forgotten`; else `Review` when `Reviews` is not empty; else `Repush` when a `Merged.Repush` flag is set). `PushingStamps.decode : string -> GroupStamps` (parsed with `System.Text.Json.JsonDocument` in Core, which the F# shared framework provides: null, empty, whitespace, `{}`, `[]`, unreadable JSON, a duplicate key, a non-object root, and a missing, non-string or unparsable key read as none for that group; the rest of the object is still read) and `encode : GroupStamps -> string option` (`None` when no stamp; else `{"content":..,"sticky":..,"tier":..}` with only the present keys in that order, `Stamp.format` text, no spaces). `rejectionKey = SyncValidation.sanitizeText`. `demotesToWarm : maxChars:int -> MergeDecision -> theirs:SyncRecord -> local:LocalEntry option -> bool` (decision 9, hot limit): true when the decision leaves a non-sticky entry in the hot tier whose text is longer than `maxChars` (UTF-16 length) **and** the decision put it there (an `InsertFromRecord`, a `Tier = Some Hot` promotion, or a content `TakeTheirs` **whose text differs from the local text** on an entry that is or becomes hot; a `TakeTheirs` that changes only project, scope, type, source or `created_at` never demotes); a decision that changes neither text nor tier never demotes, and a result that stays sticky never does (sticky is exempt; `UnpinLocally` makes the result non-sticky). `visitSet : VisitInput -> string list` (decision 5, ordinal, distinct) with `VisitInput = { Unproven: bool; Accepted: Set<string>; Changed: Set<string>; Present: Set<string>; NoBaseRows: Set<string>; ApplyFailed: Set<string>; Revisit: Set<string>; ActiveWithBase: Set<string>; LocalDeletions: Set<string> }` = (if `Unproven` then `Accepted` else `Changed`) ∪ (`NoBaseRows` ∩ `Accepted`) ∪ `ApplyFailed` ∪ `Revisit` ∪ (`ActiveWithBase` \ `Present`) ∪ `LocalDeletions`. `planRow` is in Task 2.
2. **Row plan** (decision 12.3, `SyncApply.planRow`): `RowBefore = { State: RowState option; Pending: GroupStamps; PushingText: string option; BaseTier: Tier option }`, `Comparison = { ContentHash: string; TagsHash: string; Sticky: bool; Tier: Tier }`, `RowAfter = { State: RowState; Pending: GroupStamps; PushingText: string option; Comparison: Comparison option }`, `planRow : MergeDecision -> RowBefore -> theirs:SyncRecord option -> stored:LocalEntry option -> hadEntry:bool -> colderTier:bool -> issue:(Stamp option -> Stamp option) -> Result<RowAfter option, string>`. **`Ok None` means write no row**: `RowBefore.State = None` (no row exists) and the outcome is neither `InsertFromRecord` nor `MergeGroups` (an `Ignore` with no row, W13; a `LeaveEntry` with no row, W7; a `Defer`; a `DropRow` is not a row write at all) and `decision.RowState` is `None`: such a decision creates no row, so a live entry still reaches the scan's `NewRow` and a junk row is never made. Pending per group: for `MergeGroups` the group's `StampAction` (`RestampPending` calls `issue (floorStamp (theirs's stamp for the group) (the row's pending stamp))`; `None` from `issue` is `Error`); for every other outcome `clearsPending outcome hadEntry` decides (clear all three, or keep all three). `State` is `decision.RowState` else the row's, else `Active`. `PushingText`: unchanged when no group's base became the record's, else `decode`, drop the groups whose `Base` is `BaseBecomesTheirs` (content, sticky, tier; tags carry no stamp), `encode`. `Comparison` is the hashes (`SyncScan.contentHash`, `tagsHash`), `Sticky` and `Tier` of `stored` (`None` when `stored` is `None`: columns stay). When `colderTier` is true, the pending tier stamp is kept only if the stored tier is warmer than the base's tier after the decision (the record's tier when the tier group's base became the record's, else `BaseTier`): this is the scan's `DropPendingStamp`.
3. **Store groundwork** (decisions 12 and 13, Interfaces): `SqliteStore.BeginImmediateTransaction()` (`BEGIN IMMEDIATE` through `Connection.BeginTransaction(deferred: false)`; the same single-open-transaction rule and `EndTransaction`), and `SqliteStoreTransaction` gets `internal MsSqliteConnection Connection`, `internal SqliteTransaction Transaction`, `ReplaceEmbedding(Tier, ContentType, string id, ReadOnlyMemory<float>)` (step `replace-vec`; deletes the vector row of the entry's rowid and inserts the new one, so an entry that had none gets one) and the three-tier entry read is the reader of Interpretation 4. an absent scope is written as `Scope = ""` (the column is `NOT NULL DEFAULT ''` and `ToLocalEntry` reads it back as none). `UpdateEntryOpts` gets `SourceTool` (`SourceTool?`), `ClearSourceTool` (bool) and `CreatedAt` (`long?`, unix ms), honoured by `SqlRows.UpdateRow` (`source_tool`, `created_at`); `PostgresStore.Update` throws `NotSupportedException` when any is set, as it does for scope and entry type. `GitSyncRows` gains `Read(conn, id, tx = null)`, `Delete(conn, id, tx = null)` and an optional `SqliteTransaction? tx` on `ReadAll` and `Write` (commands set `cmd.Transaction = tx`; the scanner passes none). A new `internal static class GitSyncIssues` does the `git_sync_issue` statements, all with an optional transaction: `ReadOpen(conn, kind, tx)` (id to `(record_hash, attempts, detail)`), `Upsert(conn, id, kind, recordHash, attempts, detail, tx)`, `Delete(conn, id, kind, tx)`. `SyncSql.SetMeta(conn, key, value, tx)` and `SyncSql.GetMeta(conn, key, tx)` write and read `_meta` inside a transaction (`SqliteStore.GetMeta` builds a command with no transaction and throws while one is open). The Task 3 probe test first checks what the default `Connection.BeginTransaction()` does (Microsoft.Data.Sqlite may already begin immediately); if it does, the test asserts only that `BeginImmediateTransaction` takes the lock before any statement and the deferred-versus-immediate contrast is dropped.
4. **The shared local view** (decision 7): `internal static class LocalEntryReader` with `ToLocalEntry(Entry, Tier, bool sticky)` (moved out of `GitSyncScanner`, which now calls it) and `Read(Func<Tier, Entry?> get, Func<bool> isSticky)` returning `LocalRead` (`Absent`, `Present(LocalEntry View, Tier Tier)`, `Unreadable(reason)`, `Duplicate`): an entry found in two tiers is `Duplicate`, one whose read throws (non-fatal) is `Unreadable`. The store seams are `SqliteStore.Get`/`IsSticky` and the transaction's `Get`/`IsSticky`.
5. **Base rendering** (decision 18): `internal static class BaseRenderer.Render(ParsedRecord theirs, ParsedRecord? oldBase, SyncMerge.BaseUpdate update) : string?` (UTF-8 text of the new `base_json`; `null` when the record cannot be encoded). All four groups `BaseBecomesTheirs` (or no old base): `RecordWriter.Write(theirs)` (unknown fields and `ext` namespaces kept). Mixed: build a `SyncRecord` from `theirs` with each kept group (`KeepBase`) taken from the old base (content group: text, entry type, source, project, scope, `created_at`, content stamp, `origin` and `written_by`; sticky: flag and stamp; tier: tier and stamp; tags are always the record's) and write it with `RecordWriter.WriteCore(next, tier, theirs.Unknown, theirs.UnknownSource)`; the stored tier is the old base's `StoredTier` when the tier group is kept and sticky is false, else the record's; a sticky result is written hot.
6. **Fetch types**: `FetchResult(string Head, string? Last, bool Proven, bool NothingNew)`; `abstract record FetchOutcome` with `Fetched(FetchResult)`, `NothingNew(FetchResult)`, `Refused(string Reason)`, `Failed(string Kind, string Message)` (`Kind` is `SyncGit.FailureKind` text). The constructor is `GitSyncFetcher(GitClient client, RepoGuard guard, IMetaStore meta, string branch)`; `FetchAsync(CancellationToken)`. A refused verdict's reason is `SyncIdentity.reasonText` for a not-joined state, `host identity could not be determined` for `HostUnverified`, and a fixed sentence per manifest kind (`NoClone` after a fetch is refused as `the local copy of the repository is missing`). `L` is read only when it is 40 or 64 lowercase hex characters. The proof state follows decision 2 exactly (a git call that gives no answer is `Failed`; `Tri.No`, `Tri.Unknown`, a missing ref or a ref elsewhere is unproven; a ref that is a strict ancestor of `L` is repaired with `UpdateLastSyncedAsync(L)`).
7. **Apply types and construction**: `GitSyncApplier(GitClient client, SqliteStore store, IEmbedder embedder, ApplyOptions options, Func<long> nowMs)`, `ApplyOptions(int HotMaxContentChars)`; `Task<ApplyOutcome> ApplyAsync(FetchResult fetch, ScanSummary scan, CancellationToken ct)` (the scan's `LocalDeletions` and `Skipped` are what the caller passes). `ApplyOutcome` is an abstract record with `Done(ApplySummary)` and `Failed(string Reason)`. `ApplySummary(int Inserted, int Updated, int RowsDropped, int Unchanged, int NotAttempted, bool Complete, string Head, bool Proven, IReadOnlyList<PostponedEntry> Postponed, IReadOnlyList<DeferredEntry> Deferred, IReadOnlyList<FailedEntry> Failed, IReadOnlyList<RejectedItem> Rejected, IReadOnlyList<SkippedItem> Skipped, IReadOnlyList<string> ColderTier)`; `PostponedEntry(Id, Reason)`, `DeferredEntry(Id, Reason)`, `FailedEntry(Id, Attempts, Detail)`, `RejectedItem(Key, Reason)` (`Skipped` reuses the scan's `SkippedItem`). The store's connection is the one sync uses; the embedder call is synchronous. `Updated` counts entries (not inserts, not drops) whose store or row was written, `Unchanged` decided entries that wrote neither.
8. **The entry transaction** (decision 12) is `store.BeginImmediateTransaction()`; the busy case is a `SqliteException` from it (primary code 5 or 6) and is a deferral that stops the apply. The re-read compares the mapped view with the `Local` that `decide` used, the comparison columns with the row (NULL is not compared), **and** the row read inside the transaction with the row the decision used (structural record equality; a difference is a deferral too: a decision made on a stale row is never carried out). A fault at `commit` is a failure (the transaction is rolled back and the `apply-failed` row is written). Test seams, `internal` on the applier: `Action<string>? BeforeEntry` (the id; called before the decision's inputs are read), `Action<string>? BeforeTransaction` (the id; called after `decide` and the vector, before `BEGIN IMMEDIATE`: a second connection edits here), `Action<string, string>? BeforeEntryStep` (the id and a step name; the applier sets `tx.BeforeStep = step => BeforeEntryStep?.Invoke(id, step)` so it sees the store transaction's own steps `insert-row`, `insert-vec`, `move-copy`, `move-vec`, `delete-vec`, `delete-row`, `update`, `set-sticky`, `replace-vec`, `log-import`, and adds its own `reread`, `row`, `issue` and `commit`), and `int TransactionCount` (entry transactions opened, the small clean-up ones and `DropRow`'s included).
9. **Issue texts**: `detail` of an `apply-failed` is the exception message (or a fixed text) with every `Cc` character, U+2028 and U+2029 replaced by a space and cut at 200 UTF-16 units (never cutting a surrogate pair); `scan-skipped: <reason>` and `unreadable: <reason>` use the same cleaning; `rejected-record` has `record_hash` the blob id (null when unknown), `attempts` 0 and `detail` the reason word (`SyncTree.RejectReason.describe`) or `SyncValidation.RejectModule.describe` of a validation reject (its text is already sanitised); no `ToString()` of an F# union is ever used. An identical existing row is not rewritten.
10. **`ApplyProven` is the fetch's `Proven`**; the apply does not consult the clock for anything but `RestampPending` (the persisted `git_sync_hlc`, read and written inside the entry transaction, `SyncStamp.ClockModule.issue machine nowMs clock floor`, `machine` from `git_sync_machine`; an unreadable or missing clock is treated as the scan treats a missing one: `None`). A missing machine id is a `Failed` pull ("this machine has not joined").
11. **Windows and paths**: record paths in the clone are never read from the working tree; blobs are read with `CatBlobAsync(sha, RecordReader.MaxFileBytes)`.

## Review Focus

1. A rejected or corrupt remote file is never read as a remote deletion and never stops the others [Task 6: `ARejectedPathOfAKnownId_IsNeverDecidedAsDeleted`; Task 9: `AParseRejectedRecordAtAKnownId_IsNeverDecidedAsDeleted`, `AllRejectionShapes_NeverThrow_NeverReadThroughTheWorkingTree`].
2. `L` moves only after a complete pull, `_meta` first and then the ref; a postponed, deferred, cancelled or busy-stopped pull moves neither [Task 9: `LDoesNotAdvance_ForPostponedDeferredCancelledAndBusy`, `CompletePull_WritesMetaThenRef`].
3. A scan straight after a pull stamps nothing and writes nothing, for every carried-out outcome including the hot-limit move [Task 7: `AScanRightAfter_StampsNothing_ForEveryCarriedOutOutcome`].
4. Postponed entries change nothing at all (store, rows, issues, `import_log`, vectors) [Task 7: `APostponedEntry_ChangesNothing_AndNeverCallsTheEmbedder`].
5. A fault at each step of an entry's transaction leaves everything as before; the re-read defers an edit that landed after the scan [Task 8: `AFaultAtEachStep_RollsBackEverything`, `AnEditAfterTheScan_IsDeferred_AndNeverOverwritten`].
6. The proof state: no `L`, a non-descendant, an unknown answer, a ref elsewhere or missing are unproven; a ref behind is repaired; `NothingNew` runs the guard and needs the clone to hold `L` [Task 5].
